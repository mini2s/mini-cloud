# 工作流用户旅程实现差距报告

依据：`docs/企业编程协作平台-用户旅程-工作流.md`。

检视范围：当前仓库的 Go 后端、核心 API/类型、Web/Desktop 共享视图与工作流相关 E2E/文档实现。本文只做差距检视，不包含代码修改。

## 1. 总体判断

当前代码已经具备“工作流 DAG 编排 + Issue 触发运行 + 节点运行态展示”的主干能力，但距离用户旅程文档描述的企业研发协作工作流还有明显差距。

已具备的能力主要包括：

- 工作流定义、节点、边、运行实例、节点运行实例数据表：`server/migrations/108_workflow.up.sql:7`、`server/migrations/108_workflow.up.sql:22`、`server/migrations/108_workflow.up.sql:45`、`server/migrations/108_workflow.up.sql:60`、`server/migrations/108_workflow.up.sql:78`
- 研发阶段/泳道模型：`server/migrations/125_workflow_stage.up.sql:7`
- 节点支持执行者/评审者类型为 human / agent / squad：`server/migrations/108_workflow.up.sql:32`、`server/migrations/108_workflow.up.sql:35`
- Workflow CRUD、节点/边/阶段 API、运行 API、节点提交/评审/跳过/接管/交还/完成 API：`server/cmd/server/router.go:520`
- Issue 分配 workflow 后启动 run 并创建节点子 Issue：`server/internal/handler/issue.go:2046`、`server/internal/handler/issue.go:2424`
- Issue 列表默认隐藏 workflow 节点 Issue：`server/pkg/db/queries/issue.sql:10`
- Issue 详情已有执行全景页：`packages/views/issues/components/issue-detail.tsx:1958`
- 节点接管、打开会话、交还、人工完成控制按钮：`packages/views/workflows/components/node-run-control-actions.tsx:53`

主要缺口集中在：

- 交付物定义和提交状态仍不是一等模型；
- 研发角色、岗位动态映射未建模；
- 工作流内联创建 Agent/Squad、跳转知识中心编辑 Plugin/Skill 未闭环；
- 节点 JSON Schema 仍是核心字段，与用户旅程“新增交付物定义，同时移除节点 JSON Schema”不一致；
- 执行阶段的人工任务、评审任务、重试/人工处理/提交交付物动作语义不完整；
- 企微、CSC 状态栏通知未形成工作流专属闭环；
- 代码仓库、PR 上传、代码整合节点基本未实现。

## 2. 创建/编辑工作流

### 已实现

- 工作流标题、描述、状态、最大重试次数：`server/migrations/108_workflow.up.sql:7`
- 节点标题、描述、位置、执行者、评审者、API critic、排序：`server/migrations/108_workflow.up.sql:22`
- 节点阶段归属，支持阶段创建、编辑、删除、重排：`server/migrations/125_workflow_stage.up.sql:7`、`server/cmd/server/router.go:539`
- 前端有统一 panorama/editor 页面、节点配置面板和保存逻辑：`packages/views/workflows/components/workflow-detail-shell.tsx:9`、`packages/views/workflows/components/overview/workflow-panorama-page.tsx:610`
- 前端有 DAG 预检查：环、孤点、不可达、worker 缺失、critic 引用、stage 缺失、schema 必填字段：`packages/core/workflows/preflight-checks.ts:5`、`packages/core/workflows/preflight-checks.ts:309`
- 服务端启动运行前会校验 DAG 环：`server/internal/service/workflow.go:114`、`server/internal/handler/workflow_run.go:175`

### 差距

- 缺“研发角色”模型。当前 worker/critic 只支持 `human | agent | squad | api`，没有研发角色定义、岗位动态映射、责任田/用户画像等模型。
- 缺“交付物定义”。当前节点只有 `format_schema`、`worker_output`、`critic_output`，没有 deliverable type、交付要求、PR/文档引用、提交状态字段。
- 与文档要求冲突：文档要求“新增交付物定义，同时移除节点 JSON Schema”，当前节点配置面板仍以 `format_schema` 为核心输入：`packages/views/workflows/components/node-config-panel.tsx:295`。
- 工作流内不能直接创建 Agent/Squad。Agent/Squad 作为独立页面和弹窗存在，但节点配置只是选择已有 assignee：`packages/views/workflows/components/node-config-panel.tsx:14`。
- Plugin/Skill 关联不是工作流节点级能力。Agent 表有 `plugin_id`，Agent 详情也有 Skills 关联，但 WorkflowNode 只保存 worker/critic id；节点无法声明“当前节点需要哪些 Plugin/Skill”。
- “运行时不可用时路由至其他运行时/模型”只在 Issue 选择 workflow 时做了在线 runtime 选择：`packages/views/issues/components/pickers/assignee-picker.tsx:271`，不是节点级策略，也没有模型 fallback 编排。
- DAG 环不在创建边时强制阻断。`CreateWorkflowEdge` 只校验自环和节点存在，环要靠前端 preflight 或 run 前校验发现。
- 激活流程只检查 worker/critic 缺失，未服务端统一执行完整 preflight。`UpdateWorkflow` 激活时没有调用 `ValidateDAG`。

## 3. 查看工作流执行情况

### 已实现

- Issue 分配 Workflow 自动创建 WorkflowRun 和节点子 Issue，并回写 parent issue 的 `workflow_id/workflow_run_id`：`server/internal/handler/issue.go:2053`、`server/internal/handler/issue.go:2070`
- Issue 详情全屏展示执行全景：`packages/views/issues/components/issue-detail.tsx:1958`
- 执行全景拉取 workflow、stage、node、edge、node run，并按阶段渲染：`packages/views/issues/components/execution/execution-panorama-page.tsx:55`
- 全局提示条支持 awaiting_critic、blocked/failed、awaiting_input：`packages/views/issues/components/execution/global-notification-bar.tsx:21`
- 详情面板显示节点描述、状态路径、worker、critic、输出、metadata、耗时和 retry count：`packages/views/issues/components/execution/execution-detail-panel.tsx:116`、`packages/views/issues/components/execution/execution-detail-panel.tsx:233`
- 子 Issue 页也尝试显示节点控制按钮：`packages/views/issues/components/issue-detail.tsx:1905`

### 差距

- “交付物红绿灯提交状态”未实现。当前 artifact 行只是根据 `worker_output/critic_output` 推导名称：`packages/views/issues/components/execution/runtime-node-card.tsx:165`，不是交付物清单、提交状态或 PR/文档检查。
- “进入会话”已有按钮，但与真实会话空间的体验不完整。按钮只是设置 chat session 或向 CSC 宿主发送导航：`packages/views/workflows/components/node-run-control-actions.tsx:53`；实时打印、介入、托管交还依赖外部 chat/cloud/CSC 能力，工作流页内不是完整会话空间。
- 运行时节点响应缺 worker/critic 任务区分字段。TS schema 期望 `worker_agent_task_id/critic_agent_task_id`：`packages/core/api/schemas.ts:812`，但 Go response 只返回 `agent_task_id/runtime_id/session_id`：`server/internal/handler/workflow_run.go:50`。
- `GetWorkflowRun` 后端返回 `{ run, node_runs }`，前端 `api.getWorkflowRun` 按单个 `WorkflowRunSchema` 解析，存在契约不一致风险：`server/internal/handler/workflow_run.go:204`、`packages/core/api/client.ts:2042`。

## 4. 节点内人工执行

### 已实现

- 后端有 “我的 workflow task” 查询，覆盖 human worker/critic：`server/pkg/db/queries/workflow_node_run.sql:206`
- 人工 worker 可以提交 output：`server/internal/handler/workflow_run.go:275`
- 前端提供 `useSubmitNodeRun`：`packages/core/workflows/queries.ts:239`
- 节点子 Issue 有完整 Issue 详情、评论、附件、状态等既有能力。

### 差距

- 前后端契约错误：后端 `ListMyWorkflowTasks` 返回 `tasks`，前端类型和 select 读取 `node_runs`。这会导致“我的人工节点任务”入口拿不到数据：`server/internal/handler/workflow_run.go:582`、`packages/core/workflows/queries.ts:99`、`packages/core/api/schemas.ts:832`
- “提交交付物”不是专用动作。当前 `submit` 只提交任意 `output` JSON；执行全景快捷按钮甚至固定提交 `{}`：`packages/views/issues/components/execution/execution-panorama-page.tsx:234`
- 缺交付物自检、交付物附件/PR/文档选择、交付物要求校验。
- 缺“内置协作指令”产品化入口。CLI/daemon prompt 有任务上下文和 issue 命令，但平台 UI/CSC 中没有按用户旅程列出的“查看任务清单、查看任务详情、提交交付物、流转状态”一组工作流指令。

## 5. 智能体执行、失败、纠偏、头脑风暴

### 已实现

- 状态机包含 `awaiting_input`、`blocked`、`critic_rework` 等扩展状态：`server/internal/service/workflow.go:35`
- Agent task 完成后可进入 awaiting_input，人工回复评论后可 resume：`server/internal/service/workflow.go:1254`、`server/internal/service/workflow.go:1400`
- 接管/交还支持绑定 CSC session：`server/internal/service/workflow.go:404`、`server/internal/service/workflow.go:446`
- Agent/Squad dispatch 会创建 agent task，并携带 workflow context：`server/internal/service/workflow.go:919`
- Squad worker 会解析 leader agent 执行：`server/internal/service/workflow.go:827`

### 差距

- “基于 Worktree 创建工作目录”不是 workflow 节点模型字段。daemon/agent task 有 work_dir/session 相关能力，但 workflow node/run 本身没有代码仓库、worktree 策略、目录生命周期。
- “下载 Plugin/Skill 到当前工作目录”未按 workflow 节点声明执行。当前是 Agent 关联 plugin/skill，不是 run/node-run 独立加载。
- “任务失败通知用户并设置已阻塞”有部分状态和 inbox/OS 通知基础，但没有工作流专属通知规则覆盖平台、企微、CSC 状态栏。
- “重试任务”按钮语义不正确。执行全景页 `retry` 调用的是 `handbackMutation`，不是明确重试；`complete` 调用的是 `takeoverMutation`，不是完成：`packages/views/issues/components/execution/execution-panorama-page.tsx:250`、`packages/views/issues/components/execution/execution-panorama-page.tsx:265`
- “任务分配”中智能体动态拆解依赖、人/智能体/小队分配、用户确认调整未实现为工作流内流程。当前只能静态定义 DAG 节点，运行时没有动态增删节点/依赖并请求确认的闭环。

## 6. 评审者流程

### 已实现

- 节点定义支持 critic_type / critic_id / critic_api_url：`server/migrations/108_workflow.up.sql:35`
- 人工评审 API 支持 approve/reject/comment：`server/internal/handler/workflow_run.go:324`
- 智能体评审任务完成后解析 approved/comment 并调用 ReviewNodeRun：`server/internal/service/workflow.go:1278`
- 评审通过/驳回会驱动状态机进入 completed 或 rework/blocked：`server/internal/service/workflow.go:720`

### 差距

- 人工评审入口不完整。因为 `myWorkflowTasks` 前后端字段不一致，用户可能看不到待评审任务。
- 驳回后“节点执行者是智能体：状态重置，原有会话下附评审意见继续”的语义只部分具备。服务端会 retry/rework，但 UI 没有清晰呈现“驳回意见已注入原会话继续执行”。
- 缺评审交付物读取模型。当前评审查看的是 worker_output JSON，不是“文档/PR 交付物内容”。
- 小队评审只靠 squad leader 机制，没有独立的“Leader 协调评审过程”可视化或任务分配确认。

## 7. 通知与多端协同

### 已实现

- 平台 Inbox、桌面 OS 通知、通知偏好已存在：`server/internal/handler/inbox.go:35`、`apps/desktop/src/main/index.ts:422`、`packages/views/settings/components/notifications-tab.tsx:13`
- Issue/评论/父子任务等已有平台通知基础。

### 差距

- 文档要求的平台邮箱/收件箱、手机企微通知、CSC 状态栏通知，在 workflow 节点维度没有完整事件矩阵。
- 没看到企微相关集成实现。
- CSC 状态栏通知未见工作流节点专用实现；当前更多是 session 导航和桌面 OS 通知。
- 工作流节点阻塞、待评审、待输入、失败、完成等事件没有统一通知策略和偏好分组。

## 8. 代码提交与代码整合

### 已实现

- 仓库/PR/GitHub/GitLab 相关能力在项目内存在，Issue 可以有 PR/附件/项目资源等通用能力。

### 差距

- Workflow node 没有“关联代码仓库”字段。
- 没有“将 PR 链接作为交付物上传”的工作流级交付物模型。
- 没有“代码整合节点”类型或策略。
- 没有“所有编码节点完成后自动创建整合分支、整合代码、解决冲突、记录冲突细节”的编排实现。

## 9. 优先级建议

P0：修正当前已接近可用路径的阻塞问题。

- 统一 `ListMyWorkflowTasks` 响应字段：后端返回 `node_runs` 或前端兼容 `tasks`。
- 修正 `api.getWorkflowRun` 的响应解析，避免 `{ run, node_runs }` 被当成 `WorkflowRun`。
- 在 `WorkflowNodeRunResponse` 中补齐 `worker_agent_task_id`、`critic_agent_task_id`，否则执行日志和会话区分会继续混乱。
- 修正执行全景页快捷动作语义：`retry`、`complete`、`submit` 不能映射到 handback/takeover/空 output。

P1：补齐用户旅程核心产品模型。

- 新增交付物定义：type=document/pr、要求、提交人、状态、关联附件/PR、校验结果。
- 从 `format_schema` 迁移到交付物/节点配置模型，至少先把 JSON Schema 降级为内部校验配置而非用户主入口。
- 新增研发阶段预设和研发角色模型，支持动态映射成员/Agent/Squad。
- 工作流节点配置支持跳转或内联创建 Agent/Squad，并能关联 Plugin/Skill。

P2：补齐执行协作闭环。

- 建立 workflow 事件通知矩阵：待执行、待评审、待输入、失败阻塞、完成、驳回重试。
- 为人工执行/评审提供专用任务台，而不是只依赖子 Issue 和通用评论。
- 接通会话空间中的实时查看、介入、托管交还，并在节点详情里显示会话控制权。

P3：补齐企业研发场景。

- 节点关联代码仓库、分支/worktree 策略。
- PR 交付物与代码整合节点。
- 智能体动态拆解、运行时确认、成员调整、依赖确认。
- 企微通知和 CSC 状态栏通知。

## 10. 结论

当前实现已经从“任务管理 + Agent 执行”扩展到“工作流运行框架”，但用户旅程文档描述的是更完整的“企业研发协作流程平台”。现阶段最应该优先处理的不是继续扩 UI，而是补齐契约错误和核心领域模型：交付物、评审、人工任务入口、会话/任务映射、通知事件矩阵。否则工作流看起来能跑，但很难满足文档中的真实协作闭环。
