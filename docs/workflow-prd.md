# Workflow 用户场景与产品设计说明

## 人 JOB

**搭建者**（通常是 Team Lead 或对流程有话语权的开发者）需要把团队里反复发生的多步骤任务沉淀为可复用的自动化流程，让 AI Agent 和人按既定顺序协作完成，而不是每次都在 Issue 里手动 @ agent 或人。

**使用者**（团队成员）在 Issue 被分配给一个 Workflow 后，需要一眼看懂当前执行到哪一步、谁在做什么、有没有卡住、自己是否需要介入。

**审核者**（被指定为 Critic 的成员或 Agent）需要在一个明确的节点上看到"有东西需要我审"，审完通过或打回，而不是在评论里翻找。

**非技术流程维护者**（例如运营、新员工、临时负责流程落地的人）需要从预设模板开始，少量调整人选和节点文案即可发布流程，不需要理解 DAG、JSON Schema、状态机等实现概念。

人的交互设计围绕三个时刻：
- **触发时刻**：给 Issue 分配一个 Workflow
- **观察时刻**：在全景图中看执行进度和状态
- **介入时刻**：在人工节点或失败节点上执行操作

---

## AI JOB

Workflow 的本质是**把 Issue 的完成过程从"人手动推进"变成"DAG 自动编排推进"**。AI 在其中承担两类角色：

1. **Worker**：在自动节点中，Agent 独立完成产出（写方案、改代码、生成报告等），不需要人触发。
2. **Critic**：在审核节点中，Agent 对 Worker 产出做自动检查（格式校验、代码规范、内容合规），通过则放行，不通过则打回。

产品设计的核心不是"做一个 Workflow 画布"，而是让用户感知到：**Issue 不再是等人来做的静态工单，而是一个在自动推进的、人和 AI 交替接力的执行流水线。** AI First 贯穿搭建和执行两个阶段：

- **搭建阶段**：AI 根据用户一句话描述生成 Workflow 草稿（节点、连线、Worker/Critic 建议），人审核编辑后发布。
- **执行阶段**：AI 根据结构化 Workflow 自动领取节点、产出结果、进入审核。**失败时 AI 优先尝试 self-recover**（解析结构化错误 → 调整输入重试 → 重试耗尽后升级为人工介入的可恢复状态），而非直接终止流程。人工介入的节点暴露明确的操作入口（重试/跳过/手动完成），让恢复路径可预期。

## 站在巨人肩膀上

### 编排哲学借鉴

**XSOAR — 受监督的自动化**

XSOAR 的核心思想与 Multica 的 Worker-Critic 模型高度一致——不是全自动，而是在关键节点插入人的判断。直接启示：
- **节点级状态可视化**：每个 Task 节点实时显示状态颜色+图标+耗时，人工 Task 内嵌操作按钮。
- **单节点恢复而非整流程失败**：每个 Task 有独立的 On Error 分支，验证了「跳过」「手动完成」「重试」等单节点控制 UI 的合理性。
- **可调监督级别**：Agent Critic（低监督）和 Human Critic（高监督）双层审批模型。

**Temporal — 持久执行**

Temporal 的 Durable Execution 哲学验证了 Multica 的 NodeRun 事件历史日志设计。关键启示：Signal 机制实现无限期暂停等待人工审批——节点卡片的 `awaiting_critic → human approves → resume` 交互模型正源于此。

**Dify / n8n — AI 生成草稿，人工精调后执行**

Dify 的 "AI 生成工作流" 和 n8n 的 AI Agent Node 验证了"自然语言 → 结构化 DAG"的成熟度。Multica 将此能力内建为一级功能。n8n 还有一个设计教训：画布上并排排列的节点看上去像在"同时执行"，但后端实际是串行的——Multica 在编辑器的连线展示中需要让执行顺序一目了然，避免同样的认知偏差。

### 复用与自建

**复用的：**

| 复用项 | 选型 | 验证来源 |
|--------|------|---------|
| 画布引擎 | ReactFlow（`@xyflow/react`），已在项目中 | Dify、cc-wf-studio 均基于 ReactFlow 构建 AI 工作流画布 |
| 技术栈组合 | ReactFlow + Zustand + Radix UI | cc-wf-studio 同样用这套组合构建 AI Agent 工作流画布 |
| DAG 执行模式 | 前端序列化 JSON → 后端拓扑排序执行 | Dify 采用相同架构 |
| 设计哲学 | Temporal 的持久执行与断点恢复、XSOAR 的受监督自动化 | 见「编排哲学借鉴」 |

**自建的（Multica 差异化核心）：**

| 自建项 | 理由 |
|--------|------|
| **Worker-Critic 状态机**（16 个 NodeRun 状态） | 市面上没有"执行-审核-打回-重做"的节点级状态机。XSOAR 有人工审批节点，但没有 Worker-Critic 双层审批模型 |
| **自建运行时，不套用通用编排引擎** | Temporal/n8n 的调度单元是无状态 job，跑完即止。Multica 的节点执行深度绑定 Agent Task 入队、Human takeover/handback、Issue 状态同步、WebSocket 实时推送等链路，强行嫁接通用引擎会引入双状态源 |
| **画布之上的自建渲染层** | Stage 泳道、自适应节点卡片、Worker-Critic 状态渲染、Issue 双向映射——这些是 Multica 在 ReactFlow 之上的自建增量，也是全景图体验的差异化所在 |

## 验收标准：先悦己再悦人

### 第一关（悦己）

团队内部用在日常开发任务上（Bug 修复流程、需求评审流程），评估以下场景是否顺手：

1. 创建一个 5 节点 Workflow（需求分析 → 技术方案 → 开发实现 → 代码审核 → 部署验证），从空白画布到发布，是否能在 10 分钟内完成？
2. 给一个真实 Issue assign 这个 Workflow 后，打开 Issue 详情页，能否 3 秒内判断"执行到哪了"？
3. 一个节点失败后，能否在不离开全景图的情况下配置重试并恢复？
4. 作为 Critic 收到审核请求时，能否在全景图上直接完成审核操作？

每个成员独立打分（1-5），平均 ≥ 4 分且无人 ≤ 3 分才算过；任何成员打分 ≤ 3 必须写明卡点，作为返工依据。

### 第二关（悦人）

额外考虑非 power user 场景：一个刚加入团队的运营同学，能否在 3 分钟内通过预置模板创建并发布"内容发布审核流程"，过程中只调整节点名称、负责人和审核人，不需要理解 DAG、Schema、状态机的概念。该用户独立打分 ≥ 4 才算通过第二关。

## 1. Workflow 核心概念模型

### 1.1 实体关系

- **Workflow** 包含多个 **Stage**（分组）和 **Node**（节点）
- **Stage** 对节点进行分组归属，每个节点属于一个 Stage
- **Node** 之间通过 **Edge** 连接形成 DAG（有向无环图）
- **Workflow** 被 Issue 触发后产生 **WorkflowRun**（运行实例）
- **WorkflowRun** 包含多个 **WorkflowNodeRun**（节点执行实例），每个 NodeRun 对应一个 Node 定义

### 1.2 Workflow 生命周期

- **draft**：编辑中，不可被 Issue assign
- **active**：已发布，可被 Issue assign 和触发
- **paused**：暂停，已有 Run 继续跑，新 Issue 不可 assign
- **archived**：归档，不可使用

### 1.3 节点状态机（Worker-Critic）

共 16 个状态。完整枚举如下：

| # | 状态 | 中文说明 | 类型 | 前驱 | 后继 |
|---|------|---------|------|------|------|
| 1 | `pending` | 待执行 | 顶级 | （初始） | `format_checking` / `skipped` / `cancelled` |
| 2 | `format_checking` | 格式校验中 | 顶级 | `pending` / `self_recovering` / `critic_rework` | `format_ok` / `format_failed` / `cancelled` |
| 3 | `format_ok` | 格式校验通过 | 顶级 | `format_checking` | `working` / `skipped` |
| 4 | `format_failed` | 格式校验失败 | 顶级 | `format_checking` | `self_recovering` / `blocked` |
| 5 | `working` | 执行中 | 顶级 | `format_ok` / `awaiting_input` / `self_recovering` / `blocked` | `awaiting_critic` / `awaiting_input` / `self_recovering` / `blocked` / `failed` / `completed` |
| 6 | `awaiting_input` | 等待输入 | 子状态（working 下） | `working` | `working` |
| 7 | `awaiting_critic` | 等待审核 | 顶级 | `working` / `critic_reviewing`（超时降级） | `critic_reviewing` / `skipped` |
| 8 | `critic_reviewing` | 审核中 | 顶级 | `awaiting_critic` | `critic_approved` / `critic_rework` / `awaiting_critic`（超时降级） |
| 9 | `critic_approved` | 审核通过 | 顶级 | `critic_reviewing` | `completed` |
| 10 | `critic_rework` | 审核打回 | 顶级 | `critic_reviewing` | `format_checking` |
| 11 | `self_recovering` | AI 自恢复中 | 顶级 | `working` / `format_failed` | `working` / `format_checking` / `failed` |
| 12 | `completed` | 已完成 | 顶级（终止） | `critic_approved` / `working` / `blocked` | （终止） |
| 13 | `failed` | 已失败 | 顶级（终止） | `self_recovering` / `working` / `blocked` | （终止） |
| 14 | `blocked` | 人工介入 | 顶级 | `working` / `format_failed` / `awaiting_critic`（重试耗尽） | `working`（交还）/ `completed`（手动完成）/ `skipped`（跳过）/ `failed`（标记失败） |
| 15 | `skipped` | 已跳过 | 顶级（终止） | `pending` / `format_ok` / `awaiting_critic` / `blocked` | （终止） |
| 16 | `cancelled` | 已取消 | 顶级（终止） | （运行取消时） | （终止） |

**关键路径：**

- **顺利通过**：`pending → format_checking → format_ok → working → awaiting_critic → critic_reviewing → critic_approved → completed`
- **格式校验失败（Agent Critic）**：`format_checking → format_failed → self_recovering → format_checking`（自恢复成功后重做格式校验）；`self_recovering` 重试耗尽 → `blocked`
- **格式校验失败（Human Critic）**：`format_checking → format_failed → blocked`（直接等待人工介入）
- **执行中 AI 自恢复**：`working → self_recovering → working`（自恢复成功，调整输入后重新执行）；`self_recovering → failed`（重试耗尽或遇不可恢复错误）
- **执行中等待输入**：`working → awaiting_input → working`（Worker 主动请求输入，收到输入后恢复执行）
- **审核打回**：`… → critic_rework → format_checking → format_ok → working → awaiting_critic → …`（重做时重新经过格式校验；重做触发的 `format_checking` 不消耗 retry_count；循环至 retry_count 超过 max_retries → `blocked`，等待人工处理）
- **人工介入**：`working → blocked`（人手接手，后端取消当前 Agent Task）→ `working`（人手交还，重新创建新 Agent Task），或 `blocked → completed / failed / skipped`（finalize）
- **超时降级**：`critic_reviewing` 超过阈值（默认 30 分钟）→ `awaiting_critic`（降级为人工审核，原 Agent Critic 结果作废）；`format_checking` 超时 → `format_failed`
- **跳过**：`pending / format_ok / awaiting_critic / blocked` 均可 → `skipped`
- **取消**：运行取消时进入 `cancelled`

**skip 统一语义**：无论从哪个来源状态跳过，`skipped` 的业务含义统一为「本节点标记为跳过，不产生产出，不阻塞下游，流程继续」。区别仅在于副作用：从 `pending`/`format_ok` skip 无副作用（未执行）；从 `awaiting_critic` skip 丢弃已有 Worker 产出；从 `blocked` skip 释放人工接手状态。下游节点的启动条件为「所有上游节点都处于终止状态（`completed`/`skipped`/`cancelled`）」，等同 DAG 拓扑排序入度归零。

**retry_count 说明**：`max_retries` 为 Workflow 级全局配置，默认 3 次，可在 Workflow 编辑器「设置 → 执行策略」中配置（范围 0-10）。执行失败重试、自恢复重试、格式校验失败重试共用同一个计数器；审核打回触发的重做（`critic_rework → format_checking`）不消耗 retry_count。retry_count 超过 `max_retries` 后进入 `blocked`。

### 1.4 运行时快照（MVP 定义漂移防护）

Workflow 系统中最危险的一类竞态是「定义漂移」：搭建者在编辑器中修改 Workflow 定义（增删节点、改连线、改配置），而此刻已有多个 WorkflowRun 正在执行。MVP 不做「版本快照」（无版本号、无 diff、无回滚，见第 6 节后续规划），但必须保证**已触发的 Run 不受 Workflow 定义变更影响**。

**机制：**

- **Run 创建时快照**：WorkflowRun 创建时，后端将当前 Workflow 的节点、连线、Stage、节点配置、`max_retries` 等完整序列化为 JSON，存入 WorkflowRun 的 `workflow_snapshot` 字段。此后该 Run 的所有节点调度、状态流转、配置读取均以快照为准。
- **编辑不影响活跃 Run**：搭建者在编辑器中修改 Workflow 定义后，仅影响**新触发的** Run；已有 Run 继续使用各自创建时的快照定义。
- **配置修改生效范围**（对应第 2.5 节失败恢复场景）：
  - 「仅本次生效」—— 仅修改当前 NodeRun 的运行时配置，不写入 Workflow 定义、不写入快照。
  - 「更新 Workflow 配置」—— 修改 Workflow 定义本身，仅影响未来新触发的 Run；当前 Run 不受影响（继续使用快照）。

**与「版本快照（后续规划）」的边界**：运行时快照是最基础的安全保障——每次 Run 持有一份不可变的定义副本，但没有显式版本列表、版本 diff、版本回滚能力。这些是后续「版本快照」规划的范围。

**当前实现现状**：本节描述的运行时快照机制**尚未落地**。当前 WorkflowRun 仅通过外键引用 Workflow 定义，并未在创建时冻结一份完整副本；DAG 拓扑、节点配置、`max_retries` 在运行期间均实时读取最新定义。这意味着搭建者编辑一个仍有活跃 Run 的 Workflow 时，**定义漂移风险依然存在**——已有 Run 可能读到被改动的拓扑、配置或重试上限。MVP 开发前需将本节机制作为 P1 项补齐。

## 2. 用户场景

### 2.1 场景一：搭建者从空白创建 Workflow

**场景背景**：Team Lead 发现团队的 Bug 修复流程每次都要手动推进——有人修、有人审、有人验证部署。他想把这个流程沉淀为 Workflow，之后每个 Bug Issue 自动按流程走。

**用户目标**：在 10 分钟内创建并发布一个可用的 Bug 修复 Workflow。

**触发入口**：左侧导航 → Workflows → 列表页右上角「新建 Workflow」。

**核心操作路径（两条路径并行支持）：**

**路径 A — AI 辅助创建（推荐）**：
1. 点击「新建 Workflow」→ 进入编辑器，画布空白
2. 在顶部输入框用自然语言描述流程
3. AI 分析需求 → 约 5-8 秒后返回 **Proposal**：节点列表摘要 + 流程简述 + Worker/Critic 类型建议
4. 用户审核 Proposal → 确认 / 要求调整 / 补充信息
5. 确认后进入**流式渲染阶段**：节点逐个弹入画布，连线自动连接，viewport 自动跟随
6. 所有节点渲染完成后，用户编辑调整：修改节点名称、替换 Worker/Critic 人选、增减节点、分配 Stage
7. 点击右上角「发布」→ 状态变为 active

**路径 B — 手动搭建**：
1. 点击「新建 Workflow」→ 进入编辑器，画布空白
2. 从左侧节点面板拖入节点，或从节点端口拖出连线创建新节点
3. 逐个配置节点的 Worker/Critic
4. 创建 Stage 泳道并分配节点
5. 点击右上角「发布」

**预期结果**：Workflow 状态变为 active，出现在 Workflow 列表页，可被 Issue assign。

**异常情况**：
- 静态预检查失败 → 在画布上高亮问题节点/连线，错误信息显示在底部提示栏
- 发布网络失败 → Toast 报错，保留编辑内容

### 2.2 场景二：使用者给 Issue 分配 Workflow

**场景背景**：PM 创建了一个 Bug Issue，想让它按团队的 Bug 修复流程自动推进。

**用户目标**：在 Issue 详情页中，将 Issue 分配给一个已有的 Workflow。

**触发入口**：Issue 详情页 → 右侧属性面板 → Assignee 选择器。

**核心操作路径**：
1. 点击 Assignee 选择器 → 切换到「Workflow」Tab
2. 浏览可用 Workflow 列表（显示名称、节点数、最近运行状态）
3. 选择一个 Workflow → 点击确认
4. 系统自动触发 Workflow Run，Issue 详情页切换到全景图模式

**预期结果**：Issue 的 assignee_type 变为 "workflow"，全景图显示所有节点及初始状态。

**异常情况**：
- Workflow 已被暂停或归档 → 选择器中该 Workflow 灰显，不可选
- 当前已有 Workflow 在运行 → 提示"该 Issue 已有运行中的 Workflow"
- 分配操作失败 → Toast 报错，Issue 保持原有 assignee 不变

### 2.3 场景三：团队成员在全景图中观察和介入

**场景背景**：开发同学被指定为「代码审核」节点的 Human Critic。Bug Issue 的 Workflow 跑到该节点时，他需要知道"该我审核了"并完成审核。

**用户目标**：快速定位到需要自己操作的节点，完成审核操作，不离开当前页面。

**触发入口**：打开分配了 Workflow 的 Issue 详情页。

**核心操作路径**：
1. 打开 Issue → 全景图映入眼帘
2. 「代码审核」节点卡片为橙色呼吸状态，展开显示"等待审核 — 你 · 3m"，卡片上有「通过」「打回」按钮
3. 页面顶部全局提示栏："Workflow 有 1 个节点需要你的操作 — 定位"
4. 点击节点卡片 → 右侧面板显示节点详情（Worker 产出内容、历史审核记录）
5. 审核通过 → 点击「通过」→ 节点继续流转
6. 审核打回 → 点击「打回」→ 输入打回原因 → 节点回到执行状态，Worker 重新执行

**预期结果**：审核操作即时生效，全景图节点卡片状态实时更新，下游节点开始执行。

**异常情况**：
- 审核打回超过 max_retries → 节点状态变为 blocked，卡片显示"已达重试上限，等待人工处理"
- 非指定 Critic 尝试审核 → 「通过」「打回」按钮对非 Critic 用户隐藏

### 2.4 场景四：搭建者发布并测试 Workflow

**场景背景**：搭建者完成了 Workflow 的第一次编辑，想快速验证配置是否正确。

**用户目标**：一键从编辑器跳转到真实 Issue 观察 Workflow 执行。

**触发入口**：Workflow 编辑器 → 右上角「发布并测试」。

**核心操作路径**：
1. 点击「发布并测试」→ 系统执行静态预检查
2. 检查通过 → 自动发布 + 创建测试 Issue + assign 该 Workflow
3. 自动跳转到该 Issue 的全景图
4. 在真实环境中观察节点逐个执行
5. 发现问题 → 点击「编辑 Workflow」→ 回到编辑器 → 修改 → 再次「发布并测试」

**预期结果**：从编辑器到真实执行观察，整个链路在 2-3 次点击内完成。

**异常情况**：
- 静态检查失败 → 报错信息，不发布不跳转
- 测试 Issue 创建失败 → Toast 报错，但 Workflow 已发布成功；用户可选择保留 active 或回滚为 draft

### 2.5 场景五：节点失败后的恢复

**场景背景**：「开发修复」节点因为 Agent 执行出错失败了。搭建者需要排查原因并恢复执行。

**用户目标**：找出失败原因，修改配置或切换 Agent，让节点恢复执行。

**触发入口**：Issue 全景图中红色高亮的失败节点卡片。

**核心操作路径**：
1. 失败节点卡片红色高亮，显示失败原因摘要（如"Agent 执行超时"）
2. 点击节点 → 右侧面板显示完整错误日志 + 当前节点配置
3. 发现是配置问题 → 修改配置 → 选择生效范围：「仅本次生效」或「更新 Workflow 配置」
4. 点击「重试」→ 节点使用新配置重新执行
5. 如果问题是 Agent 选择不当 → 在右侧面板切换 Worker Agent → 重试
6. 如果该节点不重要 → 点击「跳过」→ 节点标记为已跳过，继续下游
7. 如果是 Agent 产出没问题只是审核卡住 → 点击「手动完成」→ 节点标记为已完成

**预期结果**：节点恢复执行，全景图状态更新，Workflow 继续推进。

**异常情况**：
- retry_count 已达上限 → 「重试」按钮灰显，只能选择「跳过」或「手动完成」
- 修改配置保存失败 → 保留原配置，Toast 报错
- 当前用户无权限 → 「跳过」「手动完成」按钮隐藏，仅可查看错误详情

### 2.6 场景六：从模板快速创建 Workflow

**场景背景**：新加入团队的 PM 想用 Workflow 管理需求评审流程，但不会从零搭建。

**用户目标**：通过官方模板一键创建可用的 Workflow，做少量调整后发布。

**触发入口**：Workflow 列表页 → 「从模板创建」。

**核心操作路径**：
1. 点击「从模板创建」→ 弹出模板选择 Dialog
2. 浏览模板列表（每个模板显示名称、描述、节点数量）
3. 选择"需求评审流程" → 预览模板的节点结构和 Stage 分组
4. 点击「使用此模板」→ 系统克隆模板到当前工作区
5. 自动进入编辑器，Workflow 名称为"{模板名称} (副本)"
6. 用户调整节点中的 Worker/Critic 人选 → 发布

**预期结果**：30 秒内获得一个结构完整、只需调整人选的 Workflow。

**异常情况**：
- 模板包含工作区不存在的 Agent → 节点卡片上标注"Agent 缺失"，需手动选择替代
- 克隆过程失败 → Toast 报错，回到列表页

## 3. Workflow 编辑器设计

### 3.1 产品目标

单视图 DAG 编辑器，支持 Stage 泳道。搭建者在一个画布上完成节点创建、连线、Stage 分配和配置。**编辑器画布是 Workflow 可视化体验的唯一基础设施**——它同时服务于搭建态（编辑模式）和运行态（Issue 详情页全景图）。

两种创建路径并行：
- **AI 辅助创建**：用自然语言描述流程 → AI 生成节点+连线+Worker/Critic 建议 → 人审核编辑发布
- **手动搭建**：面板拖入 / 端口拖出创建节点 → 连线 → 配置 Worker/Critic

### 3.2 交互设计

**节点创建——三种方式：**

1. **AI 生成**：编辑器顶部输入框用自然语言描述流程 → AI 生成节点列表+连线+Worker/Critic 类型建议 → 一次性渲染到画布，节点卡片以弹入动画呈现 → 用户审核编辑后发布。
2. **面板拖入**：左侧节点面板按类型分组折叠（Agent 节点 / 人工节点 / Squad 节点），顶部有搜索框。拖入空白区域即创建节点，拖拽时显示半透明幽灵图预览，松手后自动吸附到 20px 网格。
3. **端口拖出创建**（参考 Coze 交互）：悬停节点边缘 → 出现「+」手柄 → 拖出虚线到空白区域 → 松手 → 弹出节点类型选择浮窗 → 选择类型 → 自动创建新节点 + 建立连线。

**节点连线：**
- 鼠标悬停节点 → 显示输入/输出端口
- 从输出端口拖到输入端口 → 创建连线
- 点击连线 → 右侧面板显示连线配置（条件表达式）
- 删除：选中连线 → Delete 键或右键菜单

**Stage 管理：**
- 画布左侧有 Stage 列表，每个 Stage 对应一条水平泳道
- 节点拖入泳道 → 自动归属该 Stage
- Stage 可折叠（双击泳道头），折叠后节点隐藏，只显示 Stage 名 + 节点数
- Stage 可拖拽排序

**画布操作：**
- 滚轮缩放、拖拽平移、自动布局
- 撤销/重做（Ctrl+Z / Ctrl+Shift+Z）
- 对齐吸附

### 3.3 静态预检查

点击「发布」或「发布并测试」时自动执行：

| 检查项 | 错误提示 | 画布标注 |
|--------|---------|---------|
| DAG 存在环路 | "检测到循环依赖：A → B → A" | 环路连线红色高亮 |
| 存在未配置 Worker 的节点 | "节点「X」缺少执行者" | 节点橙色高亮 + 图标提示 |
| 孤立节点（无入边也无出边） | "节点「X」未连接到流程中" | 节点橙色高亮 |
| 不可达节点（无法从起始节点到达） | "节点「X」无法从起始节点到达" | 节点橙色高亮 |
| Worker 引用不存在 | "节点「X」的执行者「Y」不存在" | 节点橙色高亮 + 下拉展开 |
| 未配置 Critic | "节点「X」缺少审核者" | 节点橙色高亮 + 图标提示 |
| Critic 引用不存在 | "节点「X」的审核者「Y」不存在" | 节点橙色高亮 + 下拉展开 |
| 当前用户无发布权限 | "你无权发布 Workflow，请联系管理员" | 按钮灰显，不可点击 |

检查失败 → 底部提示栏显示所有问题，同时画布高亮问题位置。用户修复后重新点击发布。

## 4. Issue 详情页 Workflow 全景图设计

### 4.1 产品目标

Issue 详情页的全景图是 Workflow 使用者的**核心操作界面**。它需要在一屏内回答四个问题：

1. **执行到哪了？** — 哪个节点在运行、哪个已完成、哪个卡住了
2. **我需要做什么？** — 有没有节点在等我操作
3. **发生了什么？** — 每个节点的产出、审核结果、耗时
4. **怎么跳转？** — 如何进入节点详情、日志、配置

全景图复用编辑器画布的 ReactFlow + Stage 泳道 + SVG 连线层渲染，区别在于：
- **画布只读**：节点不可拖拽移动，无端口手柄，无 Stage 编辑控件
- **节点卡片以运行时数据渲染**：叠加 WorkflowNodeRun 状态
- **内嵌执行操作**：审核（通过/打回）、跳过、手动完成、接手/交还等操作直接在节点卡片上提供
- **全局提示栏**：显示卡住/失败节点和待操作提示

### 4.2 核心模块

| 模块 | 功能 |
|------|------|
| **全局提示栏** | 显示卡住/失败节点数量和类型。点击「定位」→ 画布自动滚动到第一个需要操作的节点（优先级：awaiting_critic > awaiting_input > failed > blocked），目标节点高亮闪烁 |
| **Stage 泳道** | 复用编辑器 StageLane 组件，传入只读模式 + 运行时节点卡片 |
| **节点卡片** | 自适应信息密度，根据节点状态展示不同内容（见下方） |
| **SVG 连线层** | 复用编辑器连线层，连线颜色随源节点运行时状态变化（绿=已完成、蓝=运行中、灰=未开始） |
| **右侧详情面板** | 选中节点的完整运行时信息，分为概览/产物/配置三个 Tab |

### 4.3 节点卡片自适应信息层级

| 节点状态 | 卡片显示内容 | 视觉特征 |
|---------|-------------|---------|
| pending / skipped / cancelled | 标题 + 节点类型图标 | 灰色，无特殊动画 |
| format_checking / working | 标题 + Worker 头像 + 实时耗时计时器 | 脉冲光圈动画（运行中） |
| awaiting_input | 标题 + Worker 头像 + "等待输入" + 等待时长 +「提供输入」按钮 | 蓝色呼吸动画 |
| awaiting_critic | 标题 + Critic 头像 + "等待审核" + 审核人 + 等待时长 +「通过」「打回」按钮 | 橙色呼吸动画 + 内嵌操作按钮 |
| completed | 标题 + 总耗时 | 绿色对勾，卡片轻微缩小 |
| failed | 标题 + 失败原因摘要 +「重试」「跳过」「手动完成」按钮 | 红色高亮边框 |
| blocked | 标题 + 接手人 +「交还」「完成」「跳过」按钮 | 紫色边框 |

### 4.4 右侧详情面板

点击节点卡片后滑出，分为三个 Tab：

**Tab 1 — 概览**
- Worker 名称 + 产出内容预览
- Critic 名称 + 审核意见（通过/打回 + 打回原因）
- 时间线：各阶段耗时
- 重试次数 / 最大重试次数

**Tab 2 — 产物**
- Worker 产出的文件列表（可下载/预览）
- 关联的子 Issue 链接（如有）
- Agent Task 执行日志摘要

**Tab 3 — 配置**（仅 Workflow 编辑者可见）
- 节点当前配置（Worker/Critic 选择、Schema、参数）
- 「编辑此节点配置」按钮 → 跳转到 Workflow 编辑器对应节点

### 4.5 与 Issue 原有内容的切换

- **全屏模式**：全景图占据整个主区域，Issue 描述、评论折叠隐藏
- **详情模式**：全景图在原有 Issue 详情页的主区域中展示（描述下方、评论上方）
- 切换按钮在顶部工具栏常驻，Toggle 行为

## 6. MVP 与后续规划边界

| 工作区自定义模板 | 用户将已有 Workflow 标记为模板 |
| 节点级重试策略 | 覆盖 Workflow 全局 max_retries |
| 定时触发/Webhook 触发 | Workflow 除 Issue 触发外的其他触发方式 |
| 版本快照 | 每次发布生成不可变版本 |
| 并行节点分支 | 同一 Stage 内多节点并行执行 |
| 条件分支 | 基于节点输出的动态路由 |
| 运行统计仪表盘 | Workflow 执行成功率、平均耗时、瓶颈节点分析 |
