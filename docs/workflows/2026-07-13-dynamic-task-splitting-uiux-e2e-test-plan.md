# 动态任务拆分 UI/UX E2E 测试方案

> 基于 `docs/superpowers/specs/2026-07-12-dynamic-task-splitting-design.md`
> 专项范围：只验证美观性、易用性、可理解性、反馈及时性、桌面布局稳定性与基础可访问性。不覆盖调度正确性、权限、数据一致性和后端边界。

## 目标

- Split 节点在编辑、待审核、运行中、完成/失败等状态下视觉清晰且不拥挤。
- 整体界面在配色、留白、层级、字号和状态提示上保持克制、统一、耐看。
- 审核面板能让用户快速理解子任务、依赖、负责人和创建结果。
- 父 issue 进度面板能低成本追踪整体进展与异常。
- 关键操作有明确反馈、确认和错误提示。
- 主要界面在 `>= 1920x1080` 的桌面环境下不溢出、不重叠、不显得拥挤。

## 视觉基调

- 主题：安静的工作台，不做营销页式装饰。
- 颜色：深石墨作正文与边界，雾白作底，青绿色作进度与确认，琥珀色只留给提醒，红色只留给危险操作。
- 字体：偏紧凑的无衬线体系，标题和数值略重，正文保持中性，不做夸张字重跳跃。
- 版式：左到右的阅读节奏稳定，面板分区清楚，信息密度高但不挤。
- 记忆点：Split 节点的聚合进度胶囊和迷你 DAG 共同构成画面主视觉，保证一眼能看懂状态和依赖。

## 测试方式

- 使用 Playwright E2E，优先走稳定 mock 或测试夹具构造状态。
- 每个核心界面覆盖 `1920x1080` 及更大桌面视口。
- 对关键状态保留 screenshot baseline：节点卡片、审核面板、DAG、父 issue 进度面板、取消确认。
- 断言以用户可见结果为主：文本可读、按钮可达、状态可区分、内容不截断到不可理解。
- screenshot baseline 重点检查视觉层次、对齐、留白、颜色克制、边框密度和状态标签可读性。

## 场景 1：编辑器配置体验

进入 workflow 编辑器，添加 Split 节点并打开配置面板。

验证点：
- Split 节点在画布上有独立图标或形态，和普通任务节点可明显区分。
- 配置项顺序符合任务心智：子模板、模式、并发上限、失败容忍。
- barrier / pipeline 切换文案简短清楚，tooltip 能解释差异。
- `max_failures` 只在 barrier 模式出现，切换时面板高度变化不造成布局跳动。
- 未配置子模板时，预检提示靠近发布区域且能定位到 Split 节点。
- 配置面板整体观感要干净，控件间距、标题层级和分组边界一致，不出现密集堆叠。

## 场景 2：待审核状态可发现

构造 Split 节点进入 `awaiting_split_review` 状态，回到画布。

验证点：
- 节点卡片展示"待审核"和子任务数量，视觉优先级高于普通运行状态。
- 点击节点或审核按钮能打开详情面板，入口不依赖隐藏 hover。
- 节点卡片在缩放到 75% 时仍能识别状态和数量。
- 长 workflow 名称、长节点标题不会覆盖状态徽章或按钮。
- 节点卡片在高亮、边框、阴影和状态色上保持统一，不出现刺眼或过饱和的视觉效果。
- 节点卡片的留白、圆角和阴影厚度保持一致，不出现生硬拼接感。

## 场景 3：审核面板易用性

打开拆分审核面板，展示 5 个子任务，其中包含长标题、长描述、不同负责人和依赖关系。

验证点：
- 子任务列表可扫描：标题、负责人、依赖、勾选状态层级清楚。
- 长标题单行截断或合理换行，卡片高度变化不破坏列表节奏。
- 新增、删除、编辑、勾选/取消勾选都有即时视觉反馈。
- 确认按钮展示将创建的数量，例如"确认创建 (3)"。
- 当未选择任何子任务时，确认按钮禁用或给出明确提示。
- 审核面板底部操作区固定可见，长列表滚动时不会丢失主操作。
- 列表视觉密度适中，行距、卡片圆角和分隔线保持统一，看起来像同一套系统而不是拼贴。
- 审核区整体观感应像一块精修过的工作面板，而不是若干列表拼装的杂乱页面。

## 场景 4：依赖 DAG 可理解

在审核面板查看子任务 DAG，包含并行、串行和汇聚依赖。

验证点：
- 节点编号或标题能和左侧子任务列表对应。
- 依赖连线方向明确，交叉线不影响基本阅读。
- 选中列表项时 DAG 中对应节点有高亮，反向也成立。
- 循环依赖错误出现时，错误文案指出环路涉及的任务。
- DAG 画布有足够留白，节点和连线不贴边、不拥挤，整体构图清楚。

## 场景 5：运行中聚合进度

构造 `split_active` 状态，包含 done、running、failed、skipped、cancelled 多种子任务。

验证点：
- 画布节点展示聚合摘要，例如 `3 done · 1 failed · 2 running`，不同状态有可区分颜色。
- 失败态不会只靠颜色表达，需有图标、文本或可读标签。
- 实时状态变化后，节点摘要和父 issue 进度面板同步更新，加载状态不闪烁。
- 聚合内容在桌面节点内布局平衡，避免徽章、标题和图标挤成一团。

## 场景 6：父 Issue 进度面板

进入父 issue 详情页，展开任务拆分进度面板。

验证点：
- 默认折叠态能看见总体进度和异常数量。
- 展开后每个子任务显示标题、状态、负责人和跳转入口。
- 失败子任务展示错误摘要，详细错误可展开，长错误不撑破布局。
- 子任务跳转入口有清晰可点击区域，键盘焦点顺序合理。
- pipeline 模式下父节点已完成但子任务失败时，界面能表达"父流程已继续，子任务仍需处理"。
- 进度面板的标题、摘要和列表分区层级清楚，展开后不会显得像一大段纯文本。

## 场景 7：取消与危险操作

在 `split_active` 状态触发父 Split 节点取消。

验证点：
- 二次确认对话框明确说明会级联停止子任务。
- 主要危险按钮使用危险语义样式，取消按钮更容易回退。
- 确认后有 loading 或禁用态，避免重复点击。
- 完成后画布节点、父 issue 面板、子任务列表均呈现 cancelled 或终态摘要。
- 确认框布局克制，主文案、风险说明和按钮之间留白明确，不抢占主体界面视觉中心。

## 场景 8：空态、错误态和重试

覆盖 Agent 生成中、生成失败、审核提交失败、创建子 issue 失败等 UI 状态。

验证点：
- 生成中状态有持续反馈，用户知道正在等待 Agent。
- 失败态说明下一步动作，重试按钮可见且文案具体。
- 审核提交失败后保留用户已编辑内容，不把面板重置为空。
- toast、inline error 和节点状态之间不互相矛盾。
- 错误提示保持简短、明确、低干扰，不使用过多红色块面破坏整体观感。

## 通过标准

- 核心截图无明显重叠、截断、错位、闪烁或不可读文本。
- 所有主操作可通过鼠标和键盘完成。
- 状态、错误、危险操作不只依赖颜色表达。
- 小屏下不要求功能密度完全一致，但必须能完成查看、审核、确认、取消四类关键动作。
- UI/UX 专项问题单独标注，不与后端调度或数据正确性失败混在一起。
