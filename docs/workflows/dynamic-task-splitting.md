# 子任务拆分与展示 PRD

## 人 JOB
**谁**：管理复杂任务的团队负责人、PM 或技术负责人，面对一个需要拆分为多个子任务协同完成的大任务（如"迁移所有仓库到新 CI""为每个客户生成合规报告"）。

**什么问题**：当前 workflow 每个节点只能产出 0~1 个子 issue。遇到"一个任务需要拆出 N 个子任务、且子任务之间可能存在依赖关系"的场景，只能手动逐个创建、逐个指派 workflow，也无法在父任务中持续追踪整体进度。

**目标**：配置一个"任务拆分节点"，由 Agent 根据上下文智能生成子任务列表，经人审核后批量创建子 issue，各自绑定独立 workflow 并行执行；父 workflow 和父 issue 能聚合展示所有子任务的实时进展。

**边界**：拆分节点负责 Agent 驱动的智能拆分 + 人审核 + 批量创建子 issue + 进度汇总。具体执行仍交给子 WorkflowRun 内的标准节点。子任务嵌套限制为两层（父→子），子的 workflow 内不再嵌套任务拆分节点。

---

## AI JOB

### AI 负责什么
- **拆分决策由 Agent 驱动**：Agent 根据父 issue 的上下文（标题、描述、已有节点输出）生成子任务列表，包括每个子任务的标题、描述、建议负责人和子任务间依赖关系。拆分不是代码确定性逻辑，而是 Agent 理解任务语义后的智能分解。
- **审核权在人**：Agent 生成的子任务列表需要人审核通过后才能正式创建子 issue。审核人可以修改、增删子任务、调整依赖关系。
- **子任务的 AI 执行**走现有 workflow 标准路径：每个子 issue 有自己的 WorkflowRun → NodeRun → agent task，Agent 按子模板完成具体工作。

### 人在 AI First 基础上的交互设计

**触发意图**：人在 workflow 模板编辑器中将某个节点类型设为"任务拆分"，配置子 workflow template、并发上限、汇聚策略和失败策略。运行时该节点被上游激活后，Agent 生成拆分方案，人审核通过后正式创建子 issue 并启动。

**Review 角色**：
- Agent 生成的拆分方案需要在画布和父 issue 详情页中审查确认后才生效。
- 审核时人可以修改子任务内容、增删子任务、调整依赖关系，也可部分通过（只创建其中几个子任务，其余暂不创建或丢弃）。
- 必要时人可以取消父 run；父节点取消时级联停止所有子 issue 运行，同时需要防呆机制（二次确认），避免误操作导致批量取消。
- 需要更复杂审批流程时，模板作者可在拆分节点前放置现有 human 审批节点，不新增内建审批状态。

**进度心智模型**：
- `barrier` 模式：所有子任务完成后父 Split NodeRun 才释放下游，适合下游依赖子任务结果的场景。可配置允许的最大失败数，超过后父节点标记失败。
- `pipeline` 模式：子任务全部创建完成后父 Split NodeRun 立即释放下游，适合下游只依赖"任务已分发"这一事实的场景。
- `max_concurrency` 限制同时运行的子任务数量，默认 5 个；未启动项保持 pending，避免一次性启动过多工作。并发限制可在运行时调整。

**子任务依赖关系**：
- 子 issue 之间可存在串行或并行依赖（DAG 结构），由 Agent 推断或人在审核时手动定义。
- 运行时按依赖关系调度：被依赖的子任务完成后，依赖它的子任务才能启动。
- 循环依赖需在定义阶段检测并拒绝。
- 依赖关系和并发控制共同决定实际执行顺序。

## 概念统一

明确区分两个核心概念：

| 概念 | 定义 | 示例 |
|------|------|------|
| **issue**（工作项） | 具体的工作任务，有标题、描述、状态、负责人 | "迁移 user-service 到新 CI" |
| **Node**（流程图节点） | Workflow 画布上的节点，定义执行步骤和流转逻辑 | "审批节点""Agent 节点""任务拆分节点" |

**关键规则**：运行时节点不再镜像映射为子 issue。只有任务拆分节点产出的才是子 issue，其他节点（Agent 节点、human 节点等）只是流程步骤，不对应独立 issue。

## 站在巨人肩膀上

- **n8n**：Execute Workflow 节点支持调用子工作流，采用跳转独立页面查看子流程。借鉴其"子工作流作为一等公民复用"的理念。
- **Dify**：分组折叠 + 工具跳转模式。借鉴其在主图画布上聚合展示子任务摘要、按需展开的交互模式。
- **Coze (FlowGram)**：容器节点支持原地展开/折叠，嵌套深度无硬限制。借鉴其原地展开的视觉隐喻，但 FlowGram 本身不作为本仓库的渲染引擎——继续使用现有 ReactFlow/XYFlow 架构。

| 维度 | n8n | Dify | Coze | 本方案 |
|------|-----|------|------|--------|
| 子工作流机制 | Execute Workflow 节点 | 工具跳转 / 分组折叠 | 容器节点原地展开 | Split Node + 子 WorkflowRun |
| 嵌套深度 | 软约束 | 硬限制 | 递归嵌套 | 最多 2 层（父→子），子层不再嵌套拆分 |
| 拆分方式 | 配置驱动 | 配置驱动 | 配置驱动 | Agent 驱动 + 人审核 |
| 折叠展示 | N/A | 接口契约摘要 | 紧凑条 | 子 run 聚合徽章 |
| 深入子流程 | 跳转独立页面 | 工具跳转 / 分组展开 | 原地展开 | 浮层列表 + 右侧子 DAG 详情 |
| 子任务依赖 | 无 | 无 | 无 | 支持 DAG 依赖（串行/并行） |

**自建理由**：拆分节点需要与 Multica 现有的 issue 体系、WorkflowRun 状态机、agent 派发机制深度耦合。n8n/Dify/Coze 的子流程机制都是各自引擎的内建能力，无法直接集成。我们复用自己的 WorkflowRun 标准路径（issue → Run → NodeRun → agent task），拆分节点只是在入口处做 Agent 驱动的 1→N 展开 + 人审核。

**落地原则**：详细状态机、表结构、API 定义等实现细节以设计文档为准；本文只定义产品目标和验收口径。

## 验收标准：先悦己再悦人

### 第一关（悦己）—— 我们自己愿意用吗？
- [ ] 创建一个父 issue，配置任务拆分节点，Agent 自动生成合理的子任务列表（含标题、描述和依赖关系），人审核通过后所有子任务跑起来，全程流畅自然。
- [ ] 审核界面可增删改子任务、调整依赖、修改并发参数，支持部分通过（只创建选中项）。
- [ ] barrier 模式下，所有子任务完成后父节点才释放下游；失败数超阈值时父节点标记失败——不能出现"子任务还没跑完下游就开始执行"。
- [ ] pipeline 模式下，子任务创建完成父节点立即放行下游——不能卡住等子任务。
- [ ] `max_concurrency` 生效（默认 5）：超过并发上限的子任务保持 pending，并在运行中子任务终态后按依赖关系继续启动。
- [ ] 子任务 DAG 依赖生效：被依赖的子任务完成后，依赖它的子任务才开始执行；循环依赖在定义时被拒绝。
- [ ] 重复回调或事件重放不会创建重复子 issue / 子 WorkflowRun。
- [ ] 父节点取消时，防呆机制（二次确认）触发，确认后级联停止所有非终态子 issue。
- [ ] 子任务在画布上以聚合徽章展示（如 `3 completed · 1 failed · 2 running`），点击可展开查看每个子任务的状态。
- [ ] 父 issue 详情页的 workflow 进度面板能一眼看到拆分节点的整体进展。

### 第二关（悦人）—— 非 power user 也能用吗？
- [ ] 新用户首次接触任务拆分节点时，模板编辑器有足够的引导（placeholder、tooltip），不需要翻文档就能理解 Agent 拆分和审核流程。
- [ ] 子任务失败时，错误信息包含具体失败原因和定位路径（哪个子任务、哪个节点、什么错误），而不是笼统的"拆分失败"。
- [ ] `barrier`、`pipeline`、`max_concurrency` 的配置文案能让用户理解它们对下游执行时机和并发的影响。
- [ ] pending / running / completed / failed / cancelled 的子任务状态在父 issue 和画布中的显示一致。
- [ ] 子任务之间的 DAG 依赖关系在审核界面和进度面板中可视化展示，用户能直观理解执行顺序。
