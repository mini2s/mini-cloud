# Workflow 拆分任务执行者设计

## 目标

任务拆分节点不再配置或继承默认 workflow。拆分规划器只生成子 issue 草稿；拆分节点配置的审核者必须为每个待创建的子 issue 指定执行者，批准后按普通 issue 的分配规则执行。

执行者支持四种类型：

- 成员（`member`）
- 数智人（`agent`）
- 团队（`squad`）
- workflow（`workflow`）

这覆盖普通 issue 当前支持的全部执行者类型。workflow 只能由审核者为具体子 issue 选择，不能配置为拆分节点的默认 workflow。

## 方案选择

采用“草稿逐项分配”方案：拆分节点只保留规划器、审核者、并发数、失败容忍度和释放模式；拆分节点配置的审核者在审核面板中为每条子任务选择执行者，所有未丢弃任务完成分配后才能批准。

未采用以下方案：

- 节点级默认执行者：无法表达不同子任务由不同角色执行。
- 继续使用默认 workflow：与普通 issue 分配语义不同，也要求维护额外的子 workflow。
- 创建后再分配：批准不再代表计划可执行，容易产生长期无人负责的子 issue。

## 数据模型与接口

`multica_workflow_split_task` 增加可空的 `assignee_type` 和 `assignee_id`。草稿生成期间二者为空；审核接口以带版本号的更新写入执行者。批准操作必须再次校验：

- 每个未丢弃任务都同时具有 `assignee_type` 和 `assignee_id`。
- 类型只能是 `member`、`agent`、`squad` 或 `workflow`。
- 对象存在、属于当前工作区且仍可被分配。
- 当前操作人是拆分节点配置的审核者；节点使用审核角色时，以本次 workflow run 解析出的实际审核者为准。

拆分节点的审核者配置只允许成员，或最终解析为成员的角色。配置面板不展示数智人、团队和 API 审核选项；后端创建和更新拆分节点时执行相同校验。角色在运行时未解析为工作区成员时，节点不得进入可审核状态，并展示角色解析错误。

拆分草稿生成 API 和 CLI 不接受执行者字段，防止规划器编造或越权选择对象。读取接口返回执行者字段，审核更新接口允许修改执行者。

节点的 `split_config.default_issue_workflow_id` 从新建、编辑、前置检查和运行配置中移除。`SplitConfig` 只保留 `mode`、`max_concurrency` 和 `max_failures`。

## 审核交互

审核面板复用普通 issue 的完整执行者选择能力，展示成员、数智人、团队和 workflow。每条未丢弃草稿独立选择执行者；缺少执行者时显示阻断信息并禁用批准。

拆分节点的审核者是该审核流程的责任人。只有节点直接配置的审核者，或审核角色在当前 workflow run 中解析出的实际审核者，可以修改草稿执行者、丢弃草稿和批准拆分结果。其他工作区成员只能查看审核状态。

审核摘要以“已分配任务数”替代 workflow 数量。子 issue 创建后展示其执行者和 issue 状态，不再展示执行 workflow 或 workflow run 状态。

首版不增加批量分配；标题、描述、依赖和丢弃操作保持现状。

## 创建、依赖与执行

批准后按拓扑顺序创建所有未丢弃的子 issue，并保留父子关系和 `workflow_split` 来源：

- 没有未完成前置依赖的任务，创建时立即写入计划执行者。
- 有未完成前置依赖的任务，先创建为未分配 issue；计划执行者保存在拆分任务记录中。
- 当前置任务全部完成后，再把计划执行者写入后置 issue。

写入执行者后完全复用普通 issue 行为：分配给成员时等待成员处理；分配给数智人或团队时触发正常的自动执行链路；分配给 workflow 时启动所选 workflow。拆分节点不保存默认 workflow，但拆分任务通过统一的 `assignee_type` / `assignee_id` 保存审核者为该子 issue 选择的 workflow。普通 issue 分配服务按工作区规则自动挂载的默认 workflow 也保持不变；拆分调度只观察 issue 状态，不依赖具体执行引擎。

子 issue 进入 `done` 时，对应拆分任务变为 `done` 并释放依赖。子 issue 进入 `cancelled` 时，对应拆分任务变为 `cancelled`。数智人或团队的执行失败沿用普通 issue 的失败呈现和重试入口；拆分调度以 issue 状态为准，不维护独立的执行引擎重试。成员任务不提供“重试”。

## 释放模式

- `pipeline`：所有批准的子 issue 创建成功后，下游 workflow 节点即可继续；子 issue 依赖仍控制执行者何时实际分配。
- `barrier`：等待所有未丢弃子 issue 进入 `done` 或 `cancelled`。`cancelled` 和自动执行失败计入失败数；超过 `max_failures` 时拆分节点失败，否则完成并继续下游节点。

`max_concurrency` 限制当前已分配且未终结的子 issue 数量。依赖已满足但超过并发限制的任务保持未分配，直到出现可用名额。

## 历史数据

部署前已启动、且已经创建 workflow run 的拆分子任务继续按旧逻辑执行到终态，避免中断正在进行的工作。

尚未批准的历史草稿把原 `workflow_id` 迁移为 `assignee_type = 'workflow'` 和对应的 `assignee_id`，随后清除旧字段。新生成的拆分任务不再写入旧 `workflow_id`。旧节点中的 `default_issue_workflow_id` 被忽略，不提供双轨配置界面。普通 issue 分配服务后续自动挂载的默认 workflow 不回写拆分任务。

历史兼容分支只识别旧拆分任务上已经存在的 `run_id`；新任务即使选择 workflow，也通过普通 issue 分配服务启动，不写入旧拆分任务的 workflow 运行字段。

## 错误处理

- 审核更新遇到执行者不存在、跨工作区或类型不合法时返回 422。
- 非节点审核者尝试修改或批准拆分草稿时返回 403。
- 乐观锁版本不一致时返回 409，前端刷新任务和执行者数据。
- 批准事务中任一执行者校验或 issue 创建失败时整体回滚。
- 依赖释放时执行者失效，任务标记为失败并记录结构化错误，不静默改为未分配。
- 重复的批准、状态同步和依赖释放必须保持幂等。

## 验证范围

只运行相关模块测试，不执行全量测试。至少覆盖：

- 节点配置不再显示或校验默认 workflow。
- 拆分节点审核者配置只允许成员或最终解析为成员的角色，前后端校验一致。
- 审核面板支持四类执行者，并阻止批准未分配任务。
- 仅节点配置的审核者或本次运行解析出的审核者可以修改和批准草稿。
- API 拒绝非法、缺失或跨工作区执行者。
- 无依赖任务立即分配，有依赖任务在前置完成后分配。
- 数智人和团队沿用普通 issue 自动执行，成员任务等待人工完成。
- `pipeline`、`barrier`、并发限制和失败容忍度的新语义。
- 已运行旧任务继续完成，未批准旧草稿要求重新分配。
