# 工作流角色到成员智能映射方案

## 1. 文档状态

本文档定义工作流角色从“仅用于展示的占位符”升级为“在工作流启动时自动映射到工作区成员”的目标方案。

本文档取代 `workflow-role-placeholder-plan.md` 中以下运行时结论：

- 角色不再要求用户在启动前替换为具体主体。
- 包含角色的工作流不再被启动前检查直接拦截。
- 角色会在运行启动阶段映射到具体成员，并写入本次运行快照。

旧文档仍保留，用于说明角色占位符功能的历史背景。本文档是角色到成员映射能力的实施依据。

本方案依赖成员管理 PR #77。后续同步该 PR 代码后，应以其最终成员字段、组织服务客户端和权限实现为准，通过适配层消化字段差异，不在本功能中重复实现成员同步。

## 2. 背景与目标

工作流节点允许为执行者和评审者选择角色，例如“研发”“测试”或“TL”。角色可以提升模板复用能力，但字符串占位符无法直接执行，旧方案只能在启动前要求用户手动替换。

成员管理能力引入后，工作区已经具备成员范围、成员状态、职位和部门关系。新方案在启动工作流时调用组织服务获取最新组织信息，再由服务端直接调用 OpenAI-compatible 大模型，将每个角色槽位映射到当前工作区内的具体用户。

目标包括：

- 工作流编辑阶段继续选择角色，不要求提前绑定固定成员。
- 工作流启动时自动完成角色到成员的映射。
- 映射结果只影响本次运行，不修改工作流模板。
- 自动映射失败、信息不足或依赖不可用时，允许有权限的用户人工指定。
- 节点真正可执行前重新校验成员有效性。
- 映射过程可恢复、可取消、可审计，不依赖进程内临时 goroutine。
- 不改变已明确配置的成员、智能体、团队或 API 的执行逻辑。

## 3. 非目标

首版不包含：

- 将角色映射到智能体、团队或 API。
- 基于实时工作量自动均衡成员。
- 限制同一成员只能承担一个角色或节点。
- 强制执行者与评审者必须是不同用户。
- 根据经理关系、技能标签、绩效或历史任务自动决策。
- 大规模候选人的分批召回和二次模型决策。
- LLM 配置管理页面或运行时热更新。
- 模型调用计费、指标看板、告警和自动回滚。
- 邮件以外的新通知渠道。
- 独立 Worker 容器或守护进程执行模式。

## 4. 核心产品语义

### 4.1 角色作用域

- 角色属于工作区。
- 节点执行者和评审者通过稳定的 `role_id` 引用角色，不保存角色名称字符串作为正式引用。
- 角色只映射到当前工作区内的有效人类成员。
- 已明确选择成员、智能体、团队或 API 的槽位保持原有行为，不参与角色解析。
- 同一成员可以同时担任同一节点的执行者和评审者。
- 同一成员可以映射到多个节点和多个角色槽位，不设置唯一性硬约束。

### 4.2 映射时机

- 工作流启动时一次性解析全部角色槽位。
- 所有槽位解析或人工指定完成前，任何节点都不能执行。
- 部分成功的映射立即保存并冻结，但不允许已解析节点提前执行。
- 节点进入对应执行阶段前，再检查映射成员的本地有效状态。
- 执行前复核失败时，不静默调用模型重新映射，必须由用户人工重新指定。

### 4.3 运行快照

- 工作流启动时复制节点图、角色名称和职责描述快照。
- 角色在运行启动后被编辑，不影响该次运行。
- 自动或人工映射后的 `multica_user.id` 写入 `workflow_node_run`，不回写模板。
- 节点派发必须读取运行快照，不能重新读取模板中的角色或具体主体。
- 下次启动工作流时，根据最新角色描述、成员状态和组织关系重新映射。

## 5. 角色管理

### 5.1 页面与字段

在工作区设置中增加“角色管理”页面。角色表单只有两个业务字段：

- 角色名称：必填，最多 100 个字符。
- 角色职责描述：必填，最多 2,000 个字符。

工作流节点原有的标题和描述继续在节点配置中维护，不在角色管理页面重复出现。模型调用时，服务端会把节点标题和描述作为角色职责的上下文。

工作流编辑器只允许选择已经存在的工作区角色，不再支持在工作流内临时输入或创建自定义角色。角色选择器显示角色名称，并通过辅助说明或悬浮提示展示职责描述。

### 5.2 名称与权限

- 角色名称保存前去除首尾空格。
- 同一工作区内按不区分大小写的规范化名称保持唯一。
- 内置角色和自定义角色共享同一命名空间。
- 工作区 `owner` 和 `admin` 可以创建、编辑和删除自定义角色。
- 普通 `member` 只能查看角色，并在拥有工作流编辑权限时选择角色。
- 内置角色首版只读且不可删除。
- 被任一工作流引用的角色不允许删除。
- 被工作流引用的角色允许编辑；修改只影响之后新启动的运行。

### 5.3 内置角色

保留现有内置角色：

- `developer`
- `qa`
- `tech_lead`

内置角色需要提供系统默认职责描述，并以角色记录的形式参与 `role_id` 引用。不能继续只依赖前端常量解释角色语义。

## 6. 数据模型调整

数据库命名和迁移应遵循项目规范，表名使用单数 `snake_case`，迁移同时提供 `.up.sql` 和 `.down.sql`。

### 6.1 角色表

沿用并调整 `multica_workflow_role`：

```text
id
workspace_id
name
description
is_builtin
needs_description          # 仅用于标记迁移后待补充的历史角色
created_by                 # 内置角色可为空
created_at
updated_at
```

要求：

- `description` 对新建和编辑请求必填。
- 新建角色的 `needs_description` 固定为 `false`；迁移角色可以暂时为空并标记为 `true`。
- 保存 `normalized_name = lower(btrim(name))`，并对 `(workspace_id, normalized_name)` 建立唯一约束；应用层和数据库统一使用该值判断重名。
- 工作流节点的角色外键采用删除限制，服务层也要在删除前返回清晰的“角色正在被工作流使用”错误。

### 6.2 收敛现有冲突模型

当前代码中同时存在：

1. `worker_role` / `critic_role` 字符串占位符。
2. `multica_workflow_role_binding` 静态优先级绑定。
3. `worker_type = role` / `critic_type = role` 的类型扩展。

目标实现必须收敛为一套模型：

- 工作流节点保存 `worker_role_id` 和 `critic_role_id`。
- 选择角色时，对应具体主体 ID 为空。
- 选择具体主体时，对应角色 ID 为空。
- 角色由启动时 LLM 映射，不使用静态优先级绑定。
- 删除 `multica_workflow_role_binding` 及相关查询、接口和调度语义。
- 旧字符串字段仅用于一次性迁移，不作为新写接口。

具体主体与角色字段继续由数据库约束和服务端校验双重保证互斥。

### 6.3 运行节点快照

`multica_workflow_node_run` 需要保存本次运行实际使用的主体：

```text
worker_type = human
worker_id = multica_user.id
critic_type = human
critic_id = multica_user.id
```

角色来源、角色快照和映射历史不要依赖模板反查，应由角色解析记录保存。

### 6.4 角色解析槽位

新增 `multica_workflow_role_resolution`，每个节点的执行者或评审者槽位一条记录：

```text
id
workflow_run_id
workflow_node_run_id
slot_type                 # worker | critic
role_id
role_name_snapshot
role_description_snapshot
status                    # pending | resolved | needs_human | invalidated
resolved_user_id
source                    # llm | manual
reason_code
reason_detail
version
resolved_by
resolved_at
created_at
updated_at
```

约束：

- `(workflow_node_run_id, slot_type)` 唯一。
- `resolved_user_id` 保存 `multica_user.id`。
- `role_id` 允许为空，并使用 `ON DELETE SET NULL`；历史审计依赖名称和职责快照，不阻止删除已经不被工作流模板引用的自定义角色。
- 人工修改通过 `version` 实现乐观锁。
- 人工修改追加审计事件，不覆盖历史记录。

### 6.5 持久化解析任务

新增 `multica_workflow_role_resolution_job`：

```text
id
workspace_id
workflow_run_id
status                    # pending | running | succeeded | partial | failed | cancelled
attempt_count
max_attempts
org_attempt_count
llm_attempt_count
format_attempt_count
generation
scheduled_at
locked_by
lease_expires_at
heartbeat_at
last_error_code
last_error_detail
model
prompt_version
created_at
started_at
finished_at
updated_at
```

同一运行只允许一个有效的待处理或执行中任务。任务表只保存恢复执行所需的业务标识，不长期保存完整 Prompt、候选列表或模型原始响应。

### 6.6 审计与调用记录

映射审计至少记录：

- 运行、节点和槽位。
- 角色名称及职责快照。
- 最终用户。
- 来源 `llm` 或 `manual`。
- 标准原因码和简短说明。
- 模型名称、提示词版本和组织数据版本。
- 人工操作人和操作时间。

每次模型调用另外记录模型、输入/输出/总 Token、请求耗时和结果类型，用于排查问题。首版不做计费和监控。

为满足追加历史和清理要求，需要分别建立：

- `multica_workflow_role_resolution_event`：记录自动映射、人工覆盖、失效、取消和过期结果丢弃。
- `multica_workflow_role_resolution_call`：记录每次组织服务/LLM 尝试的阶段、次数、Token、耗时、结果码和脱敏错误。

槽位解析成功或被人工修改时，必须在同一事务中完成：

1. 条件更新解析槽位及版本。
2. 更新 `workflow_node_run` 中对应的 `worker_id` 或 `critic_id`。
3. 追加解析事件。
4. 如果全部槽位已经解决，幂等推进运行和入口节点状态。

任何一步失败都整体回滚，调度器不能观察到“槽位已解决但节点快照尚未写入”的中间状态。

调用记录默认保留 180 天。映射结果和人工变更记录随运行保留；删除历史运行时级联删除其解析任务和审计数据。删除工作流模板不删除历史运行。

## 7. 工作流启动状态机

### 7.1 无角色工作流

工作流不包含角色槽位时，保持现有同步启动行为和响应，不创建角色解析任务。

### 7.2 包含角色的工作流

启动接口在一个数据库事务中完成：

1. 校验启动权限和工作区级解析任务限额。
2. 创建 `workflow_run`，状态为 `resolving_roles`。
3. 创建全部 `workflow_node_run` 快照，初始状态统一为不可执行的 `blocked`。
4. 为每个角色槽位创建解析记录。
5. 当前工作区具备自动解析条件时，创建一条 `pending` 解析任务。
6. 自动解析开关关闭或配置不可用时，不创建可领取任务；把槽位置为 `needs_human`，运行直接进入 `waiting_role_assignment`，并记录标准原因码。
7. 提交事务后返回 `202 Accepted` 和运行信息。

任何一步失败时整体回滚。Worker 只能领取已经提交的任务。

### 7.3 运行状态

新增运行状态：

- `resolving_roles`：正在自动解析。
- `waiting_role_assignment`：需要人工指定或重新指定。

角色解析的技术失败不使用工作流 `failed`：

- 所有槽位完成后，入口节点变为可执行状态，运行进入 `running`。
- 初始角色解析结束后仍存在未解决槽位时，运行进入 `waiting_role_assignment`；运行开始后的槽位失效按节点级阻塞处理，运行保持 `running`。
- 只有工作流实际执行失败才使用原有失败状态。
- `resolving_roles` 和 `waiting_role_assignment` 均允许取消运行。

“全部槽位完成后开始运行”必须由单个数据库事务完成。事务使用运行状态条件保证只推进一次，把入口节点从解析专用 `blocked` 状态转换为现有调度器认可的初始可调度状态；提交后再触发派发。重复的 Worker 完成事件只能读到已经推进的状态，不能重复启动 DAG。

启动快照创建时：

- 已明确配置具体主体的节点运行记录直接复制其类型和 ID，但仍保持 `blocked`。
- 角色槽位对应的运行主体 ID 暂时为空，角色来源保存在解析槽位中。
- 数据库约束允许主体 ID 在解析专用 `blocked` 状态下为空；进入可调度状态前必须已经填充。

### 7.4 取消

取消运行时：

- 将运行标记为 `cancelled`。
- 将未完成的解析任务标记为 `cancelled`。
- 取消正在进行的 HTTP 请求；无法及时取消时，写回阶段通过版本和状态条件丢弃过期结果。

同实例取消通过本地任务注册表立即取消 context；跨实例取消由 Worker 在心跳周期内轮询任务状态并取消，目标检测延迟不超过 2 秒。即使上游请求无法立即中断，`generation` 条件写回仍保证结果不会生效。
- 保留已经生成的映射和审计记录。
- 取消后的运行不可恢复；需要执行时重新启动一个新运行。

## 8. 候选成员与组织服务

### 8.1 候选范围

自动映射只考虑：

- 已经添加到当前工作区的成员。
- 本地成员状态为 `active`。
- `user_id` 非空。
- 对应用户仍然有效。

`pending_activation`、`inactive`、已移出工作区的成员，以及未加入工作区的组织成员不能参与自动映射。

### 8.2 组织服务调用

自动映射要求组织服务实时可用：

1. 服务端先从本地成员表确定工作区候选范围。
2. 使用成员的外部用户标识批量查询组织服务。
3. 组织服务返回最新职位、部门路径和是否主部门等信息。
4. 组织服务只补充候选信息，不能扩大本地候选范围。

审计中的组织数据版本优先使用上游返回的版本、ETag 或快照时间；上游没有版本字段时，记录本次 `fetched_at` 和最小候选字段的稳定哈希，不保存完整候选快照。

本地有效成员无法在组织服务中唯一匹配时，不参与自动映射，但仍可人工指定。以下情况不能猜测：

- 外部标识缺失。
- 外部标识重复。
- 一个成员匹配到多个组织用户。
- 组织服务没有返回对应用户。

组织服务不可用或重试耗尽时，运行进入 `waiting_role_assignment`。人工选择仍可使用本地有效成员列表。

### 8.3 组织信息完整性

- `position` 或 `dept_path` 至少一项有值时，成员可以参与自动映射。
- 两项都为空时，不把该成员提交给模型。
- 信息不完整的有效成员仍可人工指定。
- 过滤后没有自动候选人时直接进入人工指定。

### 8.4 执行前复核

节点进入执行或评审阶段前，只检查 Multica 本地成员状态：

- 仍属于当前工作区。
- 状态为 `active`。
- `user_id` 非空且用户有效。

执行前不再次同步调用外部组织服务。组织同步负责更新本地状态。复核失败时，将对应槽位置为 `invalidated`，阻塞当前节点并进入人工重新指定。

运行已经进入 `running` 后，成员失效采用节点级阻塞：当前节点及其下游依赖保持阻塞，其他已经执行或位于独立并行分支的节点继续运行。运行不退回启动阶段的 `waiting_role_assignment`；运行详情通过未解决槽位单独展示“需要人工指定”。

已经开始的执行任务不因成员随后失效而被中断；只在下一次需要该成员参与前复核。

## 9. LLM 接入

### 9.1 调用方式

Multica Server 直接调用 OpenAI-compatible `/chat/completions` 接口，不通过本地守护进程。

实现方式参考 `costrict-web` 的服务端 LLM 客户端和数据库扫描 Worker，但不能照搬以下缺陷：

- 不能忽略 `context.Context`。
- 不能硬编码 120 秒超时。
- 必须限制响应体大小。
- 不能在错误和日志中写入完整上游响应。
- `running` 任务必须有租约和重启恢复机制。
- 正在执行的任务必须支持协作取消和过期结果丢弃。

业务层依赖 `WorkflowRoleResolver` 接口，OpenAI-compatible 客户端只是一个实现，方便单元测试使用 Fake Resolver。

### 9.2 服务端配置

```env
WORKFLOW_ROLE_RESOLUTION_ENABLED=false
WORKFLOW_ROLE_RESOLUTION_WORKSPACE_ALLOWLIST=

WORKFLOW_ROLE_LLM_PROVIDER=openai
WORKFLOW_ROLE_LLM_API_KEY=
WORKFLOW_ROLE_LLM_MODEL=glm-4-plus
WORKFLOW_ROLE_LLM_BASE_URL=https://open.bigmodel.cn/api/paas/v4
WORKFLOW_ROLE_LLM_MAX_OUTPUT_TOKENS=4096
WORKFLOW_ROLE_LLM_TEMPERATURE=0
WORKFLOW_ROLE_LLM_TIMEOUT_SECONDS=30

WORKFLOW_ROLE_LLM_MAX_CANDIDATES=200
WORKFLOW_ROLE_LLM_MAX_SLOTS=50
WORKFLOW_ROLE_LLM_MAX_INPUT_CHARS=100000
WORKFLOW_ROLE_WORKER_CONCURRENCY=2
WORKFLOW_ROLE_MAX_ACTIVE_JOBS_PER_WORKSPACE=5
```

配置规则：

- API Key 只能来自服务端环境变量或 Kubernetes Secret。
- Base URL、模型、超时和限制参数放入非敏感配置。
- 首版不提供页面配置和热更新；修改后通过滚动重启生效。
- 可以让 Multica 和 `costrict-web` 的密钥变量引用同一个 Secret 值，但保持独立变量名和配置边界。
- 配置缺失或无效时，不阻止 Server 启动；自动映射降级为人工指定。
- LLM 或组织服务不可用不影响主服务 readiness/liveness。

### 9.3 灰度开关

- 总开关关闭：全部工作区只允许人工指定。
- 总开关开启且白名单非空：仅白名单工作区启用自动映射。
- 总开关开启且白名单为空：全部工作区启用自动映射。
- 未启用自动映射的工作区仍可管理和选择角色。

角色解析可以在健康诊断中暴露 `enabled`、`configured`、最近成功时间、最近错误类型和任务积压数，但不得包含密钥、带查询参数的完整 URL 或成员数据。首版不建设指标看板和告警。

## 10. 模型输入与输出

### 10.1 单次请求粒度

- 先把描述缺失、输入超限等明确不能自动解析的槽位置为 `needs_human`，再按本次运行一次性提交其余未解决角色槽位。
- 每个槽位独立返回结果。
- 同一角色在不同节点可以映射到不同成员。
- 同一成员可以被多个槽位重复选择。

### 10.2 模型输入

角色槽位只包含：

- 临时槽位 ID。
- 槽位类型：执行者或评审者。
- 角色名称和职责描述快照。
- 节点标题和节点描述。

候选成员只包含：

- 本次请求生成的临时候选 ID。
- 展示名称。
- 职位。
- 部门路径。
- 是否主部门。

不得发送：

- 邮箱、手机号。
- 员工编号、组织服务外部 ID。
- Multica 内部 UUID。
- 工作区权限角色。
- 不参与本次决策的成员信息。

服务端在内存中维护临时候选 ID 到 `multica_user.id` 的映射。重试时重新读取成员和组织数据，并生成新的候选快照，不长期持久化完整候选列表。

### 10.3 输入规模

- 自动候选成员最多 200 名。
- 单次角色槽位最多 50 个。
- 结构化请求正文最多 100,000 个字符。
- 任一限制超出时，不随机截断、不简单按关键词排除，也不拆分请求，直接进入人工指定。

### 10.4 提示词安全

- 使用系统提示词明确角色、节点和成员字段都是待分析数据，不是可执行指令。
- 使用结构化 JSON 传递业务数据，不把用户内容拼接成额外指令。
- 清理不可见控制字符，保留正常多语言文本。
- 角色名称最多 100 字符，职责最多 2,000 字符。
- 模型理由最多保存 500 字符。
- 历史数据超过限制时，不静默截断后自动映射；对应槽位进入人工指定。
- 检测到明显提示词注入内容时不自动映射，并记录标准原因码。

“明显提示词注入”只指版本化的静态高风险规则，例如要求忽略系统指令、伪造候选 ID 或改变输出协议的指令片段。规则命中即转人工并可通过固定样例测试。该检测只是纵深防御，不能代替结构化输入、最小数据和服务端输出校验。

前端提供即时长度校验和字符计数，服务端使用相同规则进行最终校验。

### 10.5 输出契约

模型只能返回结构化结果：

```json
{
  "results": [
    {
      "slot_id": "slot_1",
      "status": "resolved",
      "candidate_id": "candidate_3",
      "reason_code": "matched_position",
      "reason_detail": "职责与当前职位匹配"
    },
    {
      "slot_id": "slot_2",
      "status": "needs_human",
      "reason_code": "insufficient_data",
      "reason_detail": "候选人的组织信息不足"
    }
  ]
}
```

规则：

- `status` 只允许 `resolved` 或 `needs_human`。
- 不使用模型数值置信度控制放行。
- `resolved` 必须引用本次请求中的候选临时 ID。
- `needs_human` 是正常业务结果，不按异常重试。
- 服务端忽略未定义字段，并重新校验槽位和候选 ID。
- 原因码用于页面和邮件国际化；自由文本只作为审计补充。

建议原因码至少包括：

```text
matched_position
matched_department
insufficient_data
no_candidate
candidate_limit_exceeded
slot_limit_exceeded
input_limit_exceeded
org_service_unavailable
invalid_org_identity
prompt_injection_suspected
invalid_model_output
resolver_not_configured
```

### 10.6 部分结果

- 每个槽位独立校验。
- 有效槽位立即保存为 `resolved`。
- `needs_human` 槽位进入人工指定。
- 缺失、重复、未知槽位或无效候选 ID 只影响对应槽位。
- 一个槽位无效不能导致其他有效结果被丢弃。
- 只有整体响应无法解析时才进行格式纠错重试。

## 11. Worker、重试与并发

### 11.1 部署方式

角色解析 Worker 首版运行在现有 Multica Server 进程内：

- Server 启动固定数量的 Worker。
- 多副本通过数据库 `FOR UPDATE SKIP LOCKED` 和任务租约安全竞争。
- Server 关闭时停止领取新任务，并取消正在进行的请求。
- 新实例启动后回收租约过期的 `running` 任务。
- 首版不增加独立 Worker 容器。

### 11.2 重试策略

- 组织服务超时或临时错误：最多重试 3 次，指数退避。
- LLM 超时、429 或可恢复的 5xx：最多重试 2 次。
- 模型整体格式错误：附加结构化输出纠错要求后重试 1 次。
- `needs_human`、无候选人、规模超限和明确业务校验失败：不重试。
- 启动阶段重试耗尽后，运行进入 `waiting_role_assignment`；运行中节点级重试耗尽后保持 `running` 并继续阻塞对应节点。两种情况都保留已成功映射的槽位。

错误需要按可重试、不可重试和人工处理分类。不能用字符串匹配决定核心重试语义。

三类尝试次数分别写入 `org_attempt_count`、`llm_attempt_count` 和 `format_attempt_count`。`scheduled_at` 保存下一次执行时间，重启后的 Worker 根据当前阶段和对应计数继续执行，不能用统一 `attempt_count` 推断阶段。

### 11.3 工作区限流

- 每个工作区最多同时存在 5 个 `pending` 或 `running` 角色解析任务。
- 超过限制时，启动接口返回 `429 Too Many Requests`，且不创建运行记录。
- 已进入人工指定的运行不占用该限额。
- 用户主动“重新自动映射”每个运行每分钟最多一次。

### 11.4 过期结果

Worker 写回时必须带任务 `generation` 和槽位 `version` 条件：

- 运行已取消时丢弃结果。
- 任务已被替换或取消时丢弃结果。
- 槽位已被人工修改时丢弃较早发出的模型结果。
- 过期结果记录为 `stale_result_discarded`，不能覆盖人工选择。

人工重试创建新任务或复用任务时必须递增 `generation`。旧 Worker 即使仍持有有效 HTTP 响应，也无法通过条件更新。

## 12. 人工指定

### 12.1 触发条件

以下情况进入 `waiting_role_assignment`：

- 模型主动返回 `needs_human`。
- 组织服务不可用或关联失败。
- LLM 未配置、不可用或重试耗尽。
- 候选人、槽位或输入规模超限。
- 没有合格自动候选人。
- 模型响应无法修复。
- 自动解析灰度开关未对当前工作区开启。

运行已经开始后，执行前复核发现成员失效同样触发人工处理，但只阻塞对应节点和下游依赖，不把整个运行改回 `waiting_role_assignment`。

### 12.2 权限

允许人工指定：

- 本次运行发起人。
- 工作区 `owner`。
- 工作区 `admin`。

服务端授权边界统一为：

- 发起人、`owner` 和 `admin` 可以查询人工处理原因、提交人工指定和重新自动映射。
- 取消运行沿用现有运行取消权限；查看模型具体理由仍只允许发起人、`owner` 和 `admin`。

人工选择范围是当前工作区内本地状态有效、`user_id` 非空的成员。人工选择不要求该成员具有完整职位或部门信息。

### 12.3 页面操作

- 页面展示全部角色槽位和当前映射状态。
- 未解决槽位必须选择成员。
- 模型已成功映射的槽位默认保留，但允许有权限的用户覆盖。
- 用户完成选择后点击“确认分配并继续”。
- 服务端在一个事务中校验并保存全部变更。
- 所有槽位有效后，运行自动进入 `running`。
- 成员失效或发生版本冲突时整次提交失败，不进行部分覆盖。

人工修改采用乐观锁。版本冲突返回 `409 Conflict`，页面重新获取最新数据并提示用户。

批量提交事务需要锁定对应解析槽位和节点运行记录，并在写入前再次确认节点尚未进入 `running`、`reviewing` 或终态。状态校验、槽位更新、节点快照更新和审计追加必须在同一事务中完成，避免校验后节点被并发派发。

### 12.4 修改边界

- 对应执行阶段尚未开始时，可以修改槽位。
- 节点已经进入 `running`、`reviewing` 或终态后，不能替换该阶段的负责人。
- 人工修改来源记为 `manual`，保留之前的模型映射审计。
- 人工指定始终优先于正在处理的旧模型请求。

### 12.5 重新自动映射

- 运行发起人、`owner` 和 `admin` 可以只重试未解决槽位。
- 重试时重新读取本地成员状态并调用组织服务。
- 已成功槽位默认保持不变。
- 同一运行只允许一个解析任务处于待处理或执行中。
- 用户可以直接人工指定，不必先重试。

## 13. API 调整

### 13.1 角色管理 API

增加工作区级角色 CRUD API：

- 列出角色。
- 创建角色。
- 更新角色名称和描述。
- 删除未被引用的自定义角色。

角色资源通过 `role_id` 标识。所有 UUID 边界输入必须使用项目统一的安全解析方式。

### 13.2 工作流节点 API

节点创建和更新接口改用：

```json
{
  "worker_role_id": "uuid-or-null",
  "critic_role_id": "uuid-or-null"
}
```

新写接口不再接受任意角色字符串。角色和具体主体字段互斥。

### 13.3 启动 API

- 无角色工作流：保持现有响应。
- 包含角色的工作流：返回 `202 Accepted`、运行 ID 和实际状态；已创建自动解析任务时为 `resolving_roles`，自动解析关闭或配置不可用时为 `waiting_role_assignment`。
- 超过工作区任务限额：返回 `429`，不创建运行。

前端对同步启动和异步解析统一跳转运行详情页，由运行状态决定展示内容。

### 13.4 运行角色 API

需要提供：

- 查询运行的角色槽位和映射状态。
- 批量提交人工指定。
- 对未解决槽位重新发起自动映射。
- 取消解析中的运行。

API 响应必须增加 Zod schema 和 malformed response 降级测试，确保旧桌面端不会因新增状态或字段白屏。所有服务端枚举在前端都要有未知值降级展示。


建议新增 WebSocket 事件 `workflow_role_resolution_updated` 和 `workflow_run_updated`。前端收到后只使运行详情、角色槽位和相关通知 Query 失效，不在事件处理器中直接修改业务数据。
## 14. 前端改动

共享业务页面和组件放在 `packages/views`，服务端状态继续由 TanStack Query 管理。WebSocket 只负责使相关 Query 失效，不直接写入 Zustand。

### 14.1 工作区设置

新增角色管理页面：

- 列表展示名称、描述和内置标识。
- Owner/Admin 可以创建和编辑自定义角色。
- 未被工作流引用的自定义角色可以删除。
- 被引用角色的删除按钮禁用，并展示原因。
- 普通成员只读。

### 14.2 工作流编辑器

- 保留现有执行者和评审者的角色选择逻辑。
- 角色选项改用工作区角色查询和 `role_id`。
- 移除工作流内联自定义角色入口。
- 选择角色时显示职责描述。
- 旧的“启动前必须替换角色”阻断检查改为非阻断说明。
- 角色映射不需要用户在启动前确认。

### 14.3 运行详情

增加以下状态展示：

- 正在解析角色。
- 等待人工指定。
- 角色到成员的最终映射。
- 成员失效，需要重新指定。
- 成员已分配但邮件未发送。

所有有权查看运行的人都可以看到“角色 → 成员”结果。模型具体理由只向运行发起人、Owner/Admin 展示；普通执行者和评审者只看到自己的角色、节点和任务信息。

### 14.4 人工指定面板

- 展示节点、槽位、角色名称、职责快照、当前成员和标准失败原因。
- 只能选择当前工作区内有效成员。
- 支持覆盖模型已解析结果。
- 所有未解决槽位完成后才启用“确认分配并继续”。
- 处理 `409` 版本冲突和成员失效错误。

## 15. 邮件通知

通知沿用现有邮件机制，不新增站内通知、短信或企业微信。

发送时机：

- 节点首次进入执行阶段时，向执行者发送一次执行邮件。
- 节点首次进入评审阶段时，向评审者发送一次评审邮件。
- 同一用户兼任执行者和评审者时，按阶段发送两封不同邮件。
- 自动映射失败或执行前成员失效时，向运行发起人和工作区 Owner/Admin 发送人工处理邮件。
- 人工重新指定后，如果节点已经可执行，向新成员发送一次对应邮件。

幂等键使用：

```text
workflow_run_id + workflow_node_run_id + slot_type + notification_type
```

节点状态变化和通知记录应通过现有持久化邮件机制或最小 Outbox 保证一致：

- 邮件异步发送。
- 发送失败不回滚工作流状态。
- 失败可以重试，但不能重复发送。
- 邮件不包含完整模型理由。
- 成员没有邮箱时标记为 `skipped_no_email`，不阻止执行，也不反复重试。

## 16. 安全与隐私

- API Key 仅存在服务端 Secret 中，不能返回前端或写入数据库。
- 日志不得记录完整 Prompt、完整候选列表、原始模型响应或组织成员敏感字段。
- 错误响应需要截断并脱敏。
- 模型输出全部视为不可信输入。
- 模型返回的候选 ID 必须属于本次请求。
- 最终用户必须再次校验为当前工作区有效成员。
- 角色管理、人工指定、原因查看分别执行权限校验。
- 不把未加入工作区的组织用户发送给模型。
- 模型审计说明最多保存 500 字符。

## 17. 历史数据迁移

### 17.1 内置角色

旧字符串与内置角色名称匹配时，转换为当前工作区对应内置角色的 `role_id`。

### 17.2 自定义角色

- 同一工作区内的旧自定义角色字符串按规范化名称去重。
- 为每个名称创建工作区角色记录。
- 原工作流引用替换为新角色 ID。
- 迁移生成的自定义角色描述为空，页面标记为“描述待补充”。
- 描述补充前，该角色不能自动映射；运行时进入人工指定。

### 17.3 旧静态绑定

迁移前统计并记录 `multica_workflow_role_binding` 的角色、主体类型和数量，供发布核对。静态绑定中的主体和优先级不转换为运行负责人，也不作为 LLM 候选偏好；角色定义本身可以保留，主体仍必须通过当前工作区成员和组织信息重新解析。完成核对后删除绑定表和相关调度代码，迁移日志需要明确这是有意移除的旧行为。

如果绑定指向智能体或团队，同样不转换为成员。首版角色只映射到人类用户。

### 17.4 异常数据

- 空字符串、无法识别或冲突的数据标记为待修复，不猜测角色。
- 迁移必须先生成角色记录，再替换节点引用，最后移除旧字符串写路径。
- 迁移完成后移除工作流的 `custom_roles` 内联管理入口。

为了兼容尚未升级的桌面客户端，读取响应可以在 API 边界保留必要的容错字段；新写接口只接受 `role_id`。旧客户端提交任意角色字符串时返回明确校验错误，不继续双写新旧模型。

## 18. 测试策略

### 18.1 单元测试

- 角色名称规范化、唯一性、长度和删除引用校验。
- 候选成员过滤和临时 ID 映射。
- 模型输出 schema、原因码和每槽位独立校验。
- `needs_human`、无效候选 ID 和提示词注入输入。
- 执行者与评审者映射为同一用户。
- 同一用户映射到多个节点。

### 18.2 HTTP 客户端测试

使用本地测试服务器覆盖：

- 正常 OpenAI-compatible 响应。
- 超时和上下文取消。
- 429、5xx 和不可重试 4xx。
- 超大响应体。
- 空 choices、无效 JSON 和未知候选 ID。
- 日志和错误脱敏。

### 18.3 Worker 集成测试

- 数据库并发抢占。
- `FOR UPDATE SKIP LOCKED`。
- 租约续期和过期恢复。
- 指数退避和重试耗尽。
- 取消和服务重启。
- 人工修改后丢弃过期模型结果。
- 工作区并发任务上限。

### 18.4 工作流集成测试

- 无角色工作流保持现有启动行为。
- 全部角色自动映射成功。
- 部分成功后等待人工指定。
- 组织服务不可用后人工指定。
- LLM 未配置时人工指定。
- 人工覆盖模型结果。
- 执行前成员失效后重新指定。
- 全部槽位完成前节点不能执行。
- 节点派发读取运行快照而不是模板。

### 18.5 前端测试

- 角色管理权限、表单校验和引用删除限制。
- 角色选择器使用 `role_id`。
- 解析中、等待人工和失效状态展示。
- 批量人工指定和 `409` 冲突处理。
- malformed/missing API 字段和未知枚举降级。
- WebSocket 事件只触发 Query 失效。
- 邮件失败状态展示。

CI 使用 Fake Resolver 和 Mock 组织服务，不配置真实 LLM API Key，不产生模型费用。真实 GLM 调用只在显式启用的预发布冒烟测试中执行。

### 18.6 质量样例

准备脱敏样例集，覆盖：

- 职位明确匹配。
- 部门明确匹配。
- 多名候选人都合理。
- 信息不足，需要人工指定。
- 同一用户兼任执行者和评审者。
- 多节点重复选择同一成员。
- 恶意角色描述。
- 候选人缺少职位或部门。

验收不要求模型每次选择唯一固定用户。结果落在预先定义的合理候选集合内，或正确返回 `needs_human`，即视为符合预期。

## 20. 验收标准

- Owner/Admin 可以在工作区管理名称和职责描述完整的角色。
- 被工作流引用的角色不能删除，但可以编辑。
- 工作流节点通过 `role_id` 选择执行者或评审者角色。
- 包含角色的工作流启动后返回 `202`；具备自动解析条件时进入 `resolving_roles`，否则直接进入 `waiting_role_assignment`。
- 自动映射只使用当前工作区有效成员和实时组织信息。
- 模型只能选择本次请求提供的临时候选 ID，服务端最终保存 `multica_user.id`。
- 所有角色槽位完成前，没有节点可以执行。
- 自动映射失败时，运行进入 `waiting_role_assignment`，有权限的用户可以批量人工指定。
- 人工选择和模型结果冲突时，人工选择优先。
- 节点执行前发现成员失效时，节点被阻塞并要求人工重新指定。
- 节点派发使用运行快照，模板后续修改不影响已启动运行。
- 执行者和评审者可以是同一用户，同一用户也可以承担多个槽位。
- 节点进入对应阶段时发送幂等邮件；通知失败不阻止执行。
- 服务重启、Worker 并发、任务取消和过期结果不会造成重复启动或覆盖人工结果。
- 自动映射开关关闭或依赖未配置时，普通工作流不受影响，角色运行可人工继续。

## 21. 已确认决策摘要

| 主题 | 决策 |
| --- | --- |
| 模型调用位置 | Multica Server 直接调用，不通过守护进程 |
| 协议与默认模型 | OpenAI-compatible，默认参考 GLM `glm-4-plus` |
| 异步执行 | Server 内置数据库持久化 Worker |
| 候选范围 | 当前工作区有效人类成员 |
| 组织数据 | 启动时实时调用组织服务补充 |
| 映射粒度 | 每个节点的执行者/评审者槽位 |
| 批量方式 | 一次请求处理全部未解决槽位 |
| 自动启动 | 全部槽位完成后自动运行，无需用户确认 |
| 部分成功 | 保存成功结果，整体等待未解决槽位 |
| 人工兜底 | 发起人、Owner/Admin 批量指定 |
| 执行前复核 | 使用本地成员状态，不再次调用组织服务 |
| 重映射 | 失效后不静默重映射，必须人工处理 |
| 用户重复 | 允许执行者与评审者相同，允许跨节点重复 |
| 通知 | 沿用邮件，在节点进入对应阶段时发送 |
| 配置 | 专用环境变量和 Secret，滚动重启生效 |
| 灰度 | 总开关加工作区白名单 |
| 监控 | 首版不建设指标监控，保留审计数据 |
