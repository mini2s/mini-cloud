# 工作流角色占位符实施方案

## 1. 背景

当前工作流节点的执行者和审核者直接绑定具体主体：

- 执行者：成员、Agent、Squad。
- 审核者：成员、Agent、Squad、API。

这种配置适合直接运行，但不利于模板复用。模板作者若将节点绑定到自己或当前工作空间中的主体，其他人复制模板后无法准确理解该节点原本应该由哪类岗位负责，也可能得到无效的跨工作空间引用。

本功能在原有执行者和审核者配置基础上增加“角色”概念。首期提供三个内置角色：

- 研发（`developer`）
- 测试（`qa`）
- TL（`tech_lead`）

角色只用于工作流展示和模板语义表达，不是实际执行主体。

## 2. 已确认的产品语义

角色具有以下明确边界：

- 不参与 Agent 提示词。
- 不绑定 runtime。
- 不创建 AI Agent 任务。
- 不创建人工任务。
- 不进行角色到成员、Agent 或 Squad 的自动或手动映射。
- 不参与工作流运行时调度。
- 模板复制时原样保留。
- 运行前必须由用户替换成具体执行者或审核者。

因此，角色是“岗位占位符”，用于表达“这个节点应该由什么岗位负责”；现有执行者和审核者用于表达“这个节点实际上由谁负责”。

## 3. 当前执行者和审核者如何用于 AI Agent

工作流节点当前保存：

```text
worker_type + worker_id
critic_type + critic_id
```

执行者类型为：

```text
human | agent | squad
```

审核者类型为：

```text
human | agent | squad | api
```

运行逻辑如下：

1. 成员：后端将节点推进到人工执行或人工评审状态，不创建 Agent 任务。
2. Agent：后端读取具体 Agent，解析 runtime，创建 `agent_task_queue`。
3. Squad：后端解析 Squad Leader Agent，再创建 Agent 任务。
4. API 审核者：进入外部 API 评审流程。
5. Agent 执行完成后，工作流进入评审阶段；Agent 评审结果中的 `approved` 决定通过或返工。

角色不应进入上述分支。存在角色占位符的工作流必须在启动前被拦截，避免产生无人能够处理的节点。

## 4. 数据设计

### 4.1 新增字段

在 `multica_workflow_node` 增加：

```sql
worker_role text null
critic_role text null
```

角色使用稳定代码存储，展示名称由前端国际化处理。

不将角色写入 `worker_id` 或 `critic_id`，因为这两个字段是 UUID；也不新增 `worker_type = role`，避免角色误入现有人工或 Agent 状态机。

### 4.2 数据约束

角色值仅允许：

```text
developer | qa | tech_lead
```

字段互斥规则：

```text
worker_role 有值时，worker_id 必须为空。
worker_id 有值时，worker_role 必须为空。

critic_role 有值时，critic_id 和 critic_api_url 必须为空。
具体审核者有值时，critic_role 必须为空。
```

选择角色时应原子地清空具体指派；选择成员、Agent、Squad 或 API 时应原子地清空角色。互斥规则需要同时由数据库约束和后端请求校验保障。

### 4.3 API 字段

工作流节点的创建、更新和响应增加：

```json
{
  "worker_role": "developer",
  "critic_role": "tech_lead"
}
```

字段均可为空。前端解析旧服务端响应时，应将缺失字段降级为 `null`。

## 5. 模板行为

### 5.1 模板编辑

模板作者可为节点选择角色，例如：

```text
执行者：角色 · 研发
审核者：角色 · TL
```

角色选择是现有执行者/审核者选择能力的补充，不删除成员、Agent、Squad 和 API 等原有选项。

### 5.2 模板复制

从模板创建工作流时：

- `worker_role` 和 `critic_role` 原样复制。
- 不解析或替换角色。
- 新工作流保持草稿状态。
- 用户在激活或启动前，将角色占位符改成具体主体。

### 5.3 模板发布

角色本身是合法模板配置。现有“模板只能引用内置 Agent”的检查只应用于具体 Agent/Squad 引用，不应拒绝角色占位符。

## 6. 启动与状态约束

启动工作流前，后端扫描所有可执行节点：

- 任一节点存在 `worker_role`，拒绝启动。
- 任一节点存在 `critic_role`，拒绝启动。
- 错误响应应包含节点标题、字段和角色名称，便于前端定位。

示例：

```text
节点“接口实现”的执行者仍为角色“研发”，请指定具体执行者。
```

前端可以提前展示未完成指派数量，但后端校验是最终保障，不能只依赖前端禁用按钮。

首期不修改 `dispatchWorker`、`dispatchCritic`、`DispatchAgentTask` 等运行时核心逻辑。

## 7. 前端交互

### 7.1 节点配置

在执行者和审核者选择区域增加角色分组：

```text
角色
├── 研发
├── 测试
└── TL
```

选择角色后：

- 清空当前具体主体。
- 显示“角色”类型标识和对应角色名称。
- 不显示 Agent runtime 选择。
- 用户选择具体主体后清空角色字段。

### 7.2 工作流展示

以下位置应识别角色字段：

- 工作流节点卡片。
- 节点详情面板。
- 阶段泳道和全景视图。
- 模板预览。
- 工作流启动前的未指派提示。

角色应使用独立视觉标识，避免被误认为成员或 Agent。

### 7.3 国际化

至少增加以下中英文文案：

- 角色
- 研发
- 测试
- TL
- 角色占位符
- 请在启动前指定具体执行者
- 请在启动前指定具体审核者

命名和中文文案需遵守项目 conventions 文档。

## 8. 实施步骤

### 阶段一：数据库与后端契约

1. 新增数据库迁移和约束。
2. 修改工作流节点 SQL 查询并重新生成 sqlc 代码。
3. 扩展创建、更新和响应 DTO。
4. 增加角色枚举及合法性校验。
5. 实现角色与具体主体的互斥更新。

### 阶段二：模板与启动校验

1. 模板复制时保留角色字段。
2. 确保模板发布校验允许角色。
3. 启动工作流前拦截未替换的角色。
4. 返回可定位到具体节点的错误信息。

### 阶段三：前端编辑与展示

1. 扩展 TypeScript 类型和 Zod API schema。
2. 扩展工作流编辑缓存和 mutation payload。
3. 在节点配置面板增加角色选择。
4. 更新节点卡片、详情和模板预览。
5. 增加启动前提示及中英文文案。

### 阶段四：测试与验证

1. 后端角色枚举校验测试。
2. 角色与具体主体互斥测试。
3. 模板复制保留角色测试。
4. 模板发布允许角色测试。
5. 未替换角色时启动失败测试。
6. 替换为具体主体后正常启动测试。
7. 现有成员、Agent、Squad 和 API 行为回归测试。
8. 前端 malformed/missing API 字段兼容测试。
9. 节点配置和展示组件测试。
10. 运行完整 `make check`。

## 9. 验收标准

- 用户可以把节点执行者或审核者设置为研发、测试或 TL。
- 角色在编辑器、模板预览和工作流详情中正确展示。
- 模板复制后角色保持不变。
- 角色不改变 Agent instructions 或任务 context。
- 角色不会创建人工任务或 Agent 任务。
- 存在角色占位符时工作流无法启动，并能明确指出待处理节点。
- 替换为具体成员、Agent、Squad 或 API 后，现有运行链路保持不变。
- 旧服务端未返回角色字段时，前端不会报错或白屏。

## 10. 非目标

首期明确不包含：

- 自定义角色管理。
- 角色与成员或 Agent 的关联关系。
- 自动角色匹配或负载调度。
- 角色任务池和领取机制。
- 基于角色修改 Agent prompt。
- 基于角色推荐模型或 runtime。
- 工作流运行期间动态替换执行主体。
