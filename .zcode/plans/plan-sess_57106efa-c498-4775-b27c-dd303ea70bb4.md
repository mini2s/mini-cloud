## 效能度量接口无数据 — 根因 + 修复方案

### 根因（已实测确认）
前端 `packages/core/efficiency/api.ts` 硬编码 `BASE="/kanban/api/v2"`，约 85 个接口都打到同源 `/kanban/api/v2/*`。但**这个前缀没有任何代理转发**（Next.js proxy.ts / Go router.go / nginx 都不匹配）→ 全部 404，所以数据一直不返回。

**好消息**：线上 kanban 后端（`https://zgsm.sangfor.com`）**直接接受 HTTP Basic Auth**。实测 `-u costrict:5JSvg7GYqpdLR021Q` 在 `/kanban/api/v2/dashboard/summary`、`/config`、`/users`、`/chat/stats/realtime` 等接口都返回 200 + 真实数据。所以你的判断完全正确 —— 用环境变量配账号密码注入 Basic Auth header 即可绕过手动登录，**不需要**走 Casdoor/OAuth 跳转。

### 方案：在 Go 后端加一个 kanban 反向代理（与现有 quota-manager / hub 代理同一套模式）

完全复刻 `server/internal/handler/quota_manager_proxy.go` 的成熟模式 —— 这是仓库里已有的、验证过的代理写法。

#### 1. 新建 `server/internal/handler/kanban_proxy.go`
- `func (h *Handler) KanbanProxy() http.HandlerFunc` —— `httputil.ReverseProxy`
- 目标上游：`KanbanAPIBaseURL`（= `https://zgsm.sangfor.com`）
- **路径不剥离**：前端发 `/kanban/api/v2/dashboard/summary`，上游也期望 `/kanban/api/v2/dashboard/summary`（实测一致），原样转发
- **注入 Basic Auth**：从 `KANBAN_API_USERNAME` + `KANBAN_API_PASSWORD` 组装 `Authorization: Basic base64(user:pass)`，Director 里 `req.Header.Set("Authorization", ...)`
- `ModifyResponse` 剥离上游 CORS 头（与 quota-manager 一致，避免重复头）
- `ErrorHandler` 返回 502 + 日志（与 quota-manager 一致）
- 未配置（baseURL 为空）时返回 nil → 调用方返回 503

#### 2. `server/internal/handler/handler.go` — Config 加字段
```go
// KanbanAPIBaseURL is the base URL of the efficiency-dashboard backend
// (kanban). When non-empty, /kanban/* routes are reverse-proxied here with
// HTTP Basic Auth credentials injected from KANBAN_API_USERNAME/PASSWORD.
KanbanAPIBaseURL string
```

#### 3. `server/cmd/server/router.go`
- Config 装配处加：`KanbanAPIBaseURL: strings.TrimRight(strings.TrimSpace(os.Getenv("KANBAN_API_BASE_URL")), "/")`
- 路由注册（紧挨 quota-manager 代理块，auth 组之外 —— kanban 后端用自己的 Basic Auth）：
  ```go
  if kanbanProxy := h.KanbanProxy(); kanbanProxy != nil {
      r.MethodFunc(http.MethodGet, "/kanban/*", kanbanProxy)
      r.MethodFunc(http.MethodPost, "/kanban/*", kanbanProxy)
      r.MethodFunc(http.MethodPut, "/kanban/*", kanbanProxy)
      r.MethodFunc(http.MethodDelete, "/kanban/*", kanbanProxy)
  }
  ```
  （GET/POST/PUT/DELETE 都要 —— 这些接口里有很多写操作：创建项目、更新定价、删除数据源等）

#### 4. 环境变量（`.env` / `.env.example` / `docker-compose.selfhost.yml`）
新增三个：
```
KANBAN_API_BASE_URL=https://zgsm.sangfor.com
KANBAN_API_USERNAME=costrict
KANBAN_API_PASSWORD=5JSvg7GYqpdLR021Q
```
`.env.example` 里用占位值（`https://zgsmtest.cn:30443` / 空），与现有 `QUOTA_MANAGER_API_BASE_URL` 的写法对齐。

### 为什么选 Go 代理而不是 Next.js Route Handler
- **凭据不进前端 bundle**：Basic Auth header 在服务端注入，`KANBAN_API_PASSWORD` 永远不会泄露到浏览器。若用 Next.js `NEXT_PUBLIC_*` 反而会暴露密码。
- **复用成熟模式**：仓库已有 quota-manager / hub 两个同类代理，kanban 代理结构完全一致，维护成本低。
- **一个 catch-all 路由覆盖全部 85 个接口**，不用逐个写 Route Handler。

### 不改的部分
- 前端 `api.ts` 的 `/kanban/api/v2` 前缀**不动**（已经是上游期望的路径）。
- `NEXT_PUBLIC_EFFICIENCY_MOCK` 保持默认关闭 —— 接口通了就用真实数据。

### 验证步骤
1. `cd server && go build ./...`
2. 重启 server（读 `.env` 的新变量）
3. `curl -s http://localhost:8081/kanban/api/v2/dashboard/summary -o /dev/null -w "%{http_code}"` → 期望 200
4. 浏览器访问 `/qweq/metrics` 确认数据返回
5. `make test`（确保没破坏现有代理测试）

### 风险
- Basic Auth 凭据硬编码进 `.env`（仅本地 dev 用，`.env` 不提交）。生产环境应走共享 session 或单独的密钥管理，但当前 dev 验证用 Basic Auth 完全够用。
- 所有改动在 `new-ui-demo` 工作树，暂不提交。
