## 迁移老项目 console/identity → 设置页【偏好设置】下方

把老项目 `/cloud/console/identity`(身份绑定管理:列出/绑定/解绑登录身份 + 账号合并流程)移植到当前项目的设置页,作为「我的账号」组里偏好设置下方的**新 Tab**(在 `preferences` 和 `notifications` 之间)。

### 架构方案(复用 hub 代理 — 同一 cloud-store 后端)
身份后端 `/api/auth/identities*` + `/api/auth/bind/*` 都在 cloud-store 后端。`listIdentities`/`startIdentityBind` 已在 channels 迁移时建好。只需**补全解绑/合并的代理路径 + API 方法 + 新 Tab UI**。

---

### 1. 后端 Go — 补全 hub 代理白名单 + 路由

**改** `server/internal/handler/hub_proxy.go`
- `hubProxyPaths` 追加:`"/api/auth/bind/confirm-merge"`、`"/api/auth/bind/cancel-merge"`。
  (`/api/auth/identities` 已存在 → 已覆盖 `/api/auth/identities/{provider}/unbind`;`/api/auth/bind/start` 已存在)

**改** `server/cmd/server/router.go`(hub 代理块内)
- 追加:`POST /api/auth/identities/*`(unbind)、`POST /api/auth/bind/*`(confirm-merge/cancel-merge/start 已有 GET 但 start 是 POST,补齐 POST 通配)。
  实测确认:start=POST、unbind=POST、confirm-merge=POST、cancel-merge=POST。

---

### 2. 前端 core — 补全身份 API 方法 + 复用已有查询

**已有(复用)**:`packages/core/channels/queries.ts` 的 `useIdentities()`、`api.listIdentities()`、`api.startIdentityBind()`。

**改** `packages/core/api/client.ts` — 加 3 个方法:
- `unbindIdentity(provider)` → `POST /api/auth/identities/{provider}/unbind`,返回 `{requireRelogin}`
- `confirmMerge(mergeToken)` → `POST /api/auth/bind/confirm-merge` body `{merge_token}`,返回 `{message}`
- `cancelMerge(mergeToken)` → `POST /api/auth/bind/cancel-merge` body `{merge_token}`,返回 `{message}`

**改** `packages/core/types/channels.ts` — 加 `IdentityUnbindResult { requireRelogin: boolean }`、`MergeResult { message: string }`,导出。

> 不新建独立 identity core 模块:identity 概念目前寄生在 channels(channels 的 IDTrust 门禁也用)。沿用 `@multica/core/channels` 导出 `useIdentities`/`AuthIdentity`,API 方法直接加在 `api` 上。

### 风险/开放点
- **OAuth 回调着陆页**:老版绑定后回调回 `/console/identity?bind=...`。当前项目无此路径;`startIdentityBind` 目前只传 `{provider}` 不传 redirectTo/callbackUrl(沿用 channels 的简化版)。绑定成功后上游会重定向回其默认页 —— 结果 banner(`?bind=success`)可能不会在设置页触发。这是已知的简化:核心 list/bind/unbind/merge 功能完整可用,post-bind banner 依赖上游回调配置,本地可能不完整走通。
- 所有改动在 `new-ui-demo` 工作树,暂不提交。
